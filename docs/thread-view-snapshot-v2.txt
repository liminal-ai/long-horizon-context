Here’s the repo summary:

- **What it is:** a workshop for building an **Oracle-backed agent harness** called **Total Recall**
- **Core idea:** `Model + Harness` — the model reasons, the harness gives it memory, tools, retrieval, and workflows
- **Main app:** a FastAPI “appbook” under `app/backend` + plain JS frontend in `app/frontend`
- **Learning path:** `total_recall_student.ipynb` has **19 TODOs**; `docs/todo*.md` explains each step
- **Answer key:** `total_recall_complete.ipynb`

### Main components
- `app/backend/core/db.py` — DB pool, embeddings, retrieval ladder, semantic catalog
- `app/backend/core/memory.py` — OAMP cognitive memory
- `app/backend/core/registries.py` — tool/skill registries, automations
- `app/backend/core/scratch.py` — in-DB scratch filesystem
- `app/backend/core/agent.py` — full agent loop
- `app/backend/routers/*` — API endpoints for layers, memory, skills, automations, agent loop
- `app/frontend/app.js` — browser UI and SSE streaming
- `workshop_setup.py` — shared Oracle/env plumbing
- `.devcontainer/` — Codespace/Docker setup

### How to run
- Best path: open in **GitHub Codespaces**
- Otherwise: use the devcontainer / Oracle Free + Python env
- App runs as a FastAPI service with the frontend served from the appbook

### Biggest customization points
- `agent.py` for agent behavior
- `registries.py` for new tools/skills
- `memory.py` for long-term memory behavior
- `db.py` for retrieval/vector/semantic logic
- `app/frontend/app.js` for UI / streaming behavior

Yes — very easy.

In this codebase, the materialized view is basically just the persistence mechanism for “run this SELECT and keep the latest result.” You could replace it with:

- a normal table (`CREATE TABLE AS SELECT ...`)
- a scheduler in Python (e.g. APScheduler)
- a refresh function that drops/rebuilds or `DELETE`s + reinserts rows

So a functionally equivalent tool is straightforward to build.

What you’d need to replace:
- `CREATE MATERIALIZED VIEW`
- `DBMS_MVIEW.REFRESH`
- `DBMS_SCHEDULER.*`
- the status lookup from Oracle scheduler metadata

What stays the same:
- tool signature
- validation of `select_sql`
- tracking table (`agent_automations`)
- `list_automations`, `automation_results`, etc.

So: **easy in implementation, moderate only if you want it to be production-grade**. For a workshop/demo, it’s a small change.

All work is backend.\n\nKey terms used throughout:\n\n- **Scratch filesystem** — An in-database virtual filesystem where the agent stores working files. Each file is a row (path → content). ACID-safe, survives process death.\n- **Vector store** — A table of text chunks with embedding vectors. Supports semantic (meaning-based) search via cosine distance.\n- **Retrieval ladder** — A multi-stage search pipeline: keyword search → vector search → hybrid fusion (RRF) → cross-encoder reranking. Each stage narrows and re-ranks.\n- **Cognitive memory (OAMP-equivalent)** — Thread-based conversation memory with durable facts and a context card (a rolling summary + relevant memories + recent turns assembled into one prompt-ready block).\n- **Tool registry** — A table of available tools with embedding vectors, so the agent can find the right tools by meaning rather than by name.\n- **Skill registry** — A table of reusable playbooks (SKILL.md documents) that the agent can search, load, and follow. Skills are SHA-versioned and can be imported from sources.\n- **Workflow memory** — The agent captures what it did (intent + tools used) after each turn. Recurring workflows get promoted into skills automatically.\n- **Automations** — The agent can promote a SQL query into a standing scheduled report: a results table that refreshes on a cadence, with start/stop/run-now controls.\n- **Context card** — The key context engineering mechanism. Instead of stuffing the entire conversation history into the prompt, the system produces a compact block: rolling summary + relevant durable memories + recent turns. This keeps the context window flat regardless of conversation length.\n\n---\n\n## User Profile\n\n**Primary User:** Developer building or customizing an AI agent\n**Context:** Running the harness locally — starting the backend, opening the browser UI, interacting with the agent, and extending its capabilities\n**Mental Model:** \"I have a running agent that remembers what I tell it, can query my data, learns from what it does, and gets better over time. Everything is in one place — one database file, one server process.\"\n**Key Constraint:** Must run locally with no cloud database, no Docker dependency for the database, and no GPU. The only outbound network call is to the LLM API.\n\n---\n\n## Feature Overview\n\nThis feature delivers a fully working agent harness in Python backed by SQLite. The agent can hold multi-turn conversations with persistent memory, search a knowledge base by meaning, query a seeded analytics database with safe read-only SQL, build reusable skills from its own workflows, schedule recurring reports, and keep its context window flat regardless of conversation length. Scratch Filesystem\n\nThe scratch filesystem gives the agent a durable working area for notes, drafts, and intermediate results. Files are rows in a table — path maps to content. Writes are upserts (create or overwrite). The filesystem supports read, write, list, tail, and grep. Files survive process restarts because they're in the database.\n\n1. Agent (or user via API) writes a file to a path\n2. System stores the content as a row, creating or overwriting\n3. Agent reads the file back by path\n4. Agent lists files under a root path\n5. Agent greps across all files for a pattern\n\n#### Acceptance Criteria\n\n**AC-2.1:** Files can be written and read back by path\n\n- **TC-2.1a: Write then read round-trip**\n  - Given: The scratch filesystem is initialized\n  - When: `POST /api/substrate/write` with `{\"path\": \"/notes/test.md\", \"content\": \"hello\"}` then `GET /api/substrate/read?path=/notes/test.md`\n  - Then: Read returns `{\"text\": \"hello\"}`\n- **TC-2.1b: Overwrite replaces content**\n  - Given: A file exists at `/notes/test.md` with content \"hello\"\n  - When: Write is called with the same path and content \"updated\"\n  - Then: Read returns `{\"text\": \"updated\"}`\n\n**AC-2.2:** Files can be listed under a root path\n\n- **TC-2.2a: List returns written files**\n  - Given: Files exist at `/notes/a.md` and `/notes/b.md`\n  - When: `GET /api/substrate/list?root=/notes`\n  - Then: Response contains both paths\n\n**AC-2.3:** File content can be tailed to the last N lines\n\n- **TC-2.3a: Tail returns last lines**\n  - Given: A file exists with 20 lines of content\n  - When: `GET /api/substrate/read?path=/file.txt&mode=tail&n=5`\n  - Then: Response contains only the last 5 lines\n\n**AC-2.4:** Files can be searched by regex pattern across all files\n\n- **TC-2.4a: Grep finds matching lines**\n  - Given: A file exists containing the line \"supplier risk is high\"\n  - When: `GET /api/substrate/read?mode=grep&pattern=supplier+risk&path=/`\n  - Then: Response contains a hit with the matching path, line number, and text\n- **TC-2.4b: Grep returns empty for non-matching pattern**\n  - Given: Files exist but none contain \"xyzzy\"\n  - When: Grep is called with pattern \"xyzzy\"\n  - Then: Response contains an empty hits array\n\n---\n\n### 3. Retrieval Ladder\n\nThe retrieval ladder provides four search strategies over the vector store, each building on the previous: keyword (FTS5 text search), vector (cosine distance KNN), hybrid (reciprocal rank fusion of keyword + vector), and rerank (cross-encoder rescoring of hybrid results). Text is stored as chunks with embedding vectors and metadata including a namespace for partitioning.\n\n1. Text is added to the vector store with an embedding and metadata\n2. User searches using one of four techniques: keyword, vector, hybrid, rerank\n3. System returns ranked results with scores appropriate to the technique\n\n#### Acceptance Criteria\n\n**AC-3.1:** Text can be added to the vector store with embeddings and metadata\n\n- **TC-3.1a: Added text is retrievable**\n  - Given: The vector store is empty (for the test namespace)\n  - When: A text chunk is added with namespace \"test\"\n  - Then: A subsequent vector search for that text returns it as a result\n\n**AC-3.2:** Keyword search returns results ranked by text relevance\n\n- **TC-3.2a: Keyword search finds matching text**\n  - Given: The knowledge base contains \"The Outdoors category drove Q3 revenue growth\"\n  - When: `POST /api/retrieval/search` with `{\"query\": \"revenue growth\", \"technique\": \"keyword\", \"k\": 5}`\n  - Then: Response contains hits with the matching text, each with a score\n- **TC-3.2b: Keyword search returns empty for unrelated query**\n  - Given: The knowledge base has seeded content\n  - When: Keyword search for \"quantum entanglement\"\n  - Then: Response contains zero or very low-relevance hits\n\n**AC-3.3:** Vector search returns results ranked by cosine similarity\n\n- **TC-3.3a: Vector search finds semantically similar text**\n  - Given: The knowledge base contains \"Customer churn rises sharply when delivery exceeds five days\"\n  - When: Vector search for \"shipping delays cause customer loss\"\n  - Then: The churn fact appears in the top results (semantic match, not keyword match)\n\n**AC-3.4:** Hybrid search fuses keyword and vector results using reciprocal rank fusion\n\n- **TC-3.4a: Hybrid returns results from both methods**\n  - Given: The knowledge base has seeded content\n  - When: `POST /api/retrieval/search` with `{\"query\": \"revenue\", \"technique\": \"hybrid\", \"k\": 5}`\n  - Then: Response contains hits, each with an `rrf` score\n- **TC-3.4b: RRF score is higher for items found by both methods**\n  - Given: A query matches items by both keyword and vector\n  - When: Hybrid search is performed\n  - Then: Items found by both methods have higher RRF scores than items found by only one\n\n**AC-3.5:** Reranked search rescores hybrid results with a cross-encoder\n\n- **TC-3.5a: Rerank reorders by cross-encoder score**\n  - Given: The knowledge base has seeded content\n  - When: `POST /api/retrieval/search` with `{\"query\": \"main operational risk\", \"technique\": \"rerank\", \"k\": 5}`\n  - Then: Response contains hits, each with a `rerank_score` (float)\n- **TC-3.5b: Rerank reports availability**\n  - Given: The cross-encoder model is loaded\n  - When: Any retrieval search is performed\n  - Then: Response contains `rerank_available: true`\n\n**AC-3.6:** The retrieval endpoint reports which technique was used\n\n- **TC-3.6a: Technique echoed in response**\n  - Given: Any search request\n  - When: The response is returned\n  - Then: Response contains `technique` matching the requested technique\n\n---\n\n### 4. Cognitive Memory\n\nCognitive memory gives the agent persistent memory across turns and sessions. It supports conversation threads (ordered messages), durable fact storage (remember/recall by meaning), a context card (compressed working memory for the prompt), and procedural workflow memory (capture what the agent did, recall similar past workflows). The memory-backed chat endpoint streams responses over SSE and updates the context card after each turn.\n\n1. User sends a message on a thread\n2. System records the user turn, generates a context card, calls the LLM, streams the response\n3. System records the assistant turn and updates the context card\n4. User stores a durable fact\n5. User recalls facts by meaning\n6. Agent workflow is captured after a tool-using turn\n7. Agent recalls similar past workflows before acting\n\n#### Acceptance Criteria\n\n**AC-4.1:** The memory chat endpoint streams responses over SSE and maintains conversation threads\n\n- **TC-4.1a: Chat returns SSE stream with delta and done events**\n  - Given: The LLM API key is configured\n  - When: `POST /api/memory/chat` with `{\"message\": \"hello\", \"thread_id\": \"test-1\"}`\n  - Then: Response is an SSE stream containing `delta` events (text chunks) and a `done` event with a `card` field\n\n**AC-4.2:** Conversation turns are persisted and retrievable\n\n- **TC-4.2a: Turns survive round-trip**\n  - Given: A message has been sent on thread \"test-1\"\n  - When: `GET /api/memory/turns?thread_id=test-1`\n  - Then: Response contains the user message and assistant reply in order\n\n**AC-4.3:** Durable facts can be stored and recalled by meaning\n\n- **TC-4.3a: Remember then recall round-trip**\n  - Given: No facts have been stored\n  - When: `POST /api/memory/remember` with `{\"fact\": \"The CEO is Jane Smith\"}` then `POST /api/memory/recall` with `{\"query\": \"who is the CEO\"}`\n  - Then: Recall returns a hit containing \"The CEO is Jane Smith\" with a distance score\n- **TC-4.3b: Recall returns empty for unrelated query**\n  - Given: Facts have been stored about the CEO\n  - When: Recall is called with \"quantum physics\"\n  - Then: No closely matching hits are returned\n\n**AC-4.4:** The context card is a compact summary of working memory\n\n- **TC-4.4a: Context card is non-empty after conversation**\n  - Given: Multiple turns have occurred on a thread\n  - When: `GET /api/memory/card?thread_id=test-1`\n  - Then: Response contains a non-empty `card` string\n\n**AC-4.5:** Workflow memory captures the agent's actions and deduplicates by intent similarity\n\n- **TC-4.5a: Workflow is captured after tool use**\n  - Given: The agent has completed a turn using tools\n  - When: `GET /api/skills/workflows`\n  - Then: Response contains a workflow entry with intent, occurrences, and promoted status\n- **TC-4.5b: Similar workflows are merged rather than duplicated**\n  - Given: A workflow with intent \"compute revenue by category\" exists\n  - When: A new workflow with intent \"calculate revenue by product category\" is captured\n  - Then: The existing workflow's occurrence count increments rather than creating a new row\n\n**AC-4.6:** Past workflows can be recalled by meaning\n\n- **TC-4.6a: Recall returns similar workflows**\n  - Given: Workflows have been captured\n  - When: The agent recalls workflows for \"revenue analysis\"\n  - Then: The revenue-related workflow is returned with intent, steps, and occurrence count\n\n**AC-4.7:** Past conversation threads can be listed and re-read\n\n- **TC-4.7a: Thread listing returns past conversations**\n  - Given: Conversations have occurred on multiple threads\n  - When: `GET /api/memory/threads`\n  - Then: Response lists threads with message count, last activity, and a preview\n- **TC-4.7b: Thread messages can be retrieved**\n  - Given: A thread has messages\n  - When: `GET /api/memory/thread?thread_id=test-1`\n  - Then: Response contains all messages in order\n\n---\n\n### 5. Semantic Catalog\n\nThe semantic catalog embeds schema metadata (column names, types, foreign keys, comments) as vectors so the agent can discover relevant tables and columns by meaning rather than by name. The catalog is scanned from the live database schema and stored in the vector store with namespace \"semantic.\"\n\n1. System scans the schema on startup (columns, types, foreign keys, comments)\n2. System embeds each schema fact and stores it in the vector store\n3. Agent searches the catalog by meaning (e.g., \"what holds revenue data?\")\n\n#### Acceptance Criteria\n\n**AC-5.1:** The semantic catalog is populated from the live schema on startup\n\n- **TC-5.1a: Catalog contains column facts**\n  - Given: The commerce schema is seeded\n  - When: `POST /api/semantic/search` with `{\"query\": \"customer name\", \"k\": 3}`\n  - Then: Response contains a hit referencing CUSTOMERS.NAME or similar column\n\n**AC-5.2:** The semantic catalog is searchable by meaning\n\n- **TC-5.2a: Meaning-based search finds relevant schema facts**\n  - Given: The catalog is populated\n  - When: Semantic search for \"which tables have revenue\"\n  - Then: Results include facts about v_revenue or order_items with pricing columns\n- **TC-5.2b: Foreign key relationships are discoverable**\n  - Given: The catalog is populated\n  - When: Semantic search for \"how do orders connect to customers\"\n  - Then: Results include the foreign key relationship between orders and customers\n\n---\n\n### 6. The agent can create automations via a tool call, and the UI can manage them directly.\n\n1. Agent or user creates an automation with a name, SELECT query, and cadence\n2. Then: Response contains `error`\n\n**AC-7.2:** Automations can be listed with their schedule state\n\n- **TC-7.2a: List returns all automations with state**\n  - Given: An automation has been created\n  - Given: An automation exists\n  - When: `POST /api/automations/run` with `{\"name\": \"rev_by_cat\"}`\n  - Then: Response contains `refreshed` (table name) and `rows` (array of result rows)\n\n**AC-7.4:** An automation's schedule can be started and stopped\n\n- **TC-7.4a: Toggle disables an enabled automation**\n  - ```python

```

### 2. Automation “atomic replacement” is not atomic as written

Design says failed refresh preserves the last successful table, but `_rebuild_table()` uses separate committed `db.x()` calls:
```python
CREATE TABLE table_new AS ...
DROP TABLE table
ALTER TABLE table_new RENAME TO table
```
Since `db.x()` commits each statement, failure after `DROP TABLE` can destroy the old result table. That violates TC-7.5c.

**Fix:** specify an explicit transaction for replacement:
```sql
BEGIN IMMEDIATE;
DROP TABLE IF EXISTS old;
ALTER TABLE new RENAME TO old;
COMMIT;
```
with rollback on error, or use a safer swap strategy. The design should explicitly state this.
