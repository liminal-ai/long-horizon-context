# Bad Code Log

Append-only working log of poor code habits and design choices encountered while cleaning up the LHC architecture, domain surfaces, naming, and documentation.

In `messages.edit(thread, input)`, the second argument is not just arbitrary input; it is a message edit carrying `messageId` and `content`. In `messages.deleteMessage(thread, input)`, the second argument is a deletion target carrying `messageId`. The generic name makes implementation easier to stamp out but makes the public surface less readable and less domain-shaped.

- Misplaced mechanical surface on a domain: LHC is an in-process SDK for durable long-horizon conversation context. The desired architecture is domain surfaces for conversation-model concepts (`messages`, `turns`, `thread-view`, `inspect`) over shared technical utilities such as storage, token counting, logging, and the durable work queue. `messages.listQueuedWork` is a concrete bad example: it is exposed on the messages domain, but it returns raw queue rows and speaks queue vocabulary (`workItemId`, owner, kind, source ref, status, queued time). That is not message behavior; it is work-queue mechanics filtered to owner=`messages`. The bad choice is putting a mechanical queue inspection method on a product/domain surface because the queue rows happen to point at message-owned work. This blurs ownership, encourages callers to reason about queue internals through a domain namespace, and makes the messages API less coherent. The right choice is for messages to expose domain-level derivation state and repair operations, such as a message derivation report and requeue-by-derivation target, while shared-tech or an explicit work surface exposes queue inspection with filters like owner, kind, source ref, status, or source version. - Generic wrapper drift: taking a clear, specific operation shape and turning it into a vague extensibility container. In this session, the starting point was the bad existing shape `messages.requeue(thread, target)`, which exposed queue mechanics and asked for a derivation target. We refined the desired domain operation to a synchronous message derivation call: derive the message-owned derivation for these message ids. The good shape was `messages.derive(threadRef, messageIds)`, where `messageIds` is a `string[]`; it says exactly what the caller has and lets the messages domain decide what each message can derive. The bad model move was repeatedly trying to turn that into `messages.derive(threadRef, request)` or `messages.derive(threadRef, { messageIds })`. That added a generic wrapper with no current purpose, created wiggle room for future options before a need existed, and obscured the direct domain meaning. This is a common AI coding failure: the model reaches for generic API templates (`input`, `request`, `target`, `opts`) because they are common and feel extensible, but they make early-stage domain surfaces mushier and easier to pollute with unrelated fields later. Repo root: `/Users/leemoore/code/pi-long-horizon/liminal-context`. Commit: `0ed3749`. Example files: `packages/lhc/src/messages/index.ts`; planned cleanup target: replace async/mechanical `messages.requeue` thinking with a direct synchronous `messages.derive(threadRef, messageIds)` domain operation.

- Isolated permutation tests that bypass the real entry point: adding or exposing a low-level pure function just so tests can enumerate state permutations instead of exercising the service operation that owns the real contract. In this repo, `turns.transition` was exported from the turns surface and tested by `packages/lhc/test/state-machine.test.ts` as a pure rule table: every event kind in no-open-turn and open-turn states. That looks exhaustive, but it avoids the harder and higher-signal work of sending real batches through `intakeStream.messageEvents` and predicting the actual durable results: event order, message ids, turn transitions, message membership, queued turn work, skipped-event behavior, and rollback behavior. The failure mode is coverage inflation with reduced signal. The test proves a local permutation table, but it does not prove the broader path where invalid states are filtered, membership is stamped, messages are created, turns are opened/closed, queue rows are written, and reads return the expected durable state. This pattern can be valid for code with many highly specified state permutations where the state machine itself is a real public/product contract or where service-level scenarios cannot reasonably cover important states. That is not this case. Here the valid states are best reached through the normal intake surface. The better test shape is to drive `intakeStream.messageEvents`, then assert the returned `turnTransitions`, `messages.list` membership, `turns.listTurns` records, and queued turn work only where a real turn close occurred. That forces the test author to understand the data entering the front door and the exact states the application should reach, instead of bypassing the integrated path and getting a false sense of safety from isolated permutations.
