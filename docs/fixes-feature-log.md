## Architecture

### 32. Offline batch repair/refinement lane
**What:** A slow, scheduled (offline/overnight) derivation pass that walks whole transcripts with a big model at batch-API pricing (~50% off) and re-derives quality problems live lanes can't fix. First target: voice-transcription noise — Wispr garbles like ".l8c"/"Sequel Light"/"Daria" survive live smoothing (single-prompt scope can't infer referents) and then get preserved as vocabulary by faithful compressors (observed in the 2026-07-05 375k compact: garbles carried into brief/detailed bands verbatim). Batch scope fixes this: read the whole thread first, build the thread's glossary, then normalize garbles against it — grounded inference instead of guessing. Re-derivation cascades ride the existing queue (fixed smoothed prompt → re-derive consuming turn compression → chunk brief follows).
**Constraint (bake in from day one):** repairs write to the derivation store whenever, but swap into the *served* view only at rebuild boundaries (compact/rehydrate/prune-restart) — same rule as memory-index injection — or the nightly sweep torches the prefix cache every morning.
**Origin:** Lee, 2026-07-05, after reviewing compact quality.

### 17. LHC-owned native inference (default), callbacks demoted to substitution point
**What:** lhc ships its own direct HTTP inference client (OpenRouter/OpenAI/Cerebras — chat-completions, explicit reasoning effort, wire-truth logging) as the default derivation lane. Host inference callbacks stay as the substitution point for constrained environments, not the load-bearing requirement. Rationale: every mystery this round lived below the callback boundary (item 12; codex-lane instruction wrapping); prompt-lab's direct ~50-line fetch has been trivially observable and controllable all week; the wrapper hosts (items 9/10) have no host registry to bridge anyway; identical serving path across pi-lhc/cc-lhc/web means prompts tune once. Constrained-environment example: at work the enterprise Claude Code seat may be the only model access — a ClaudeCodeSubprocessProvider (claude -p one-shots) implements the callback interface as a knowingly degraded lane (harness-mediated inference is never neutral: derivation prompts land under Claude Code's own system prompt — same failure class as the codex lane).

### 21. Inference provider/model-selection layer (scoped deliberately)
**What:** The provider layer for item 17's native inference. Provider/model selection always looks easy and becomes a headache as permutations fan out — this is one of the genuinely hard parts of this space: not cognitive intricacy like the intake→domain→derivation→work-queue machinery, but finding the right balance of inference options offered in a flexible yet constrained way.
**Shape:** OpenAI chat-completions API only — this layer submits single turns to models (or model harnesses); no multi-turn, no chat streaming. Providers: `openrouter`, `cerebras`, `cc-cli` (Claude Code `-p` subprocess), `openai-codex` (ChatGPT OAuth), and possibly `z.ai` (GLM coding plan / chat API). Within a provider: a curated subset of models and a set of **common thinking options** — selectable enums tied to a model config (or a customizing function) that yields the provider's model string, maps our standard thinking levels to that provider's settings, and handles provider quirks (e.g., OpenRouter subprovider pinning). Look at PI's providers for openrouter/cerebras/openai-codex/z.ai as starting points.
**Sequencing:** OpenRouter alone until basics are dialed. Explicit dependency: a high-speed inexpensive provider (Cerebras) must be in place before any tool-call inference or any derivation that fires on a large percentage of message events (item 11's bar: provably drains at intake speed).

### 20. Thread-level system + base prompts
**What:** lhc gets first-class thread concepts for a **system prompt** and a **base prompt**. System prompt is served in the system slot. Base prompt is like the thread's first prompt — sets agent identity, scope, core qualities/history — and is updatable periodically as project direction shifts or the role adjusts (unlike a literal first message, it isn't frozen in the record's past; it rides the head of the served view across compacts). pi-lhc provides slash commands to view and update both.
**Per-model dimension (Lee, 2026-07-04 — decisions-registry material):** the broader concept — customizing/optimizing per agent model via model config plus **discrete extensions flipped on and off based on the loaded model** — is a standing architecture decision, first concrete case: the memory-maintenance protocol block. Claude models (Opus/Fable) have RL'd memory write-side reflexes and need only a pointer; models without that training (GPT, GLM 5.1, etc.) need the full protocol spelled out (when to write, format, update-don't-duplicate) and possibly active nudges at re-render boundaries. Shape: extensions can contribute both tools and system-prompt sections; the active model selects which extensions load (profile key should be model-tier, not model-name, to avoid per-point-release proliferation). Prompt contributions must compose deterministically (fixed order, stable text) and be captured into the render per item 30/27 fidelity — model-swap on a thread is a rebuild boundary. Factoring principle: the **record stays model-neutral forever; the served rendering becomes a function of (thread, model-profile)**. This is the first sanctioned breach of served-context model-neutrality; keep it the only one until something else earns it.

### 29. `/lhc-tool-prune`: manual tool-result prune via the visibility boundary — DONE 2026-07-03, see Done section
**What:** A slash command that relieves context pressure without a full smart compact: advance the visibility boundary forward so tool results older than a target render as their 500-char truncations (pointer back to the record), leaving prompts/text/thinking untouched. Successor to the POC's automatic 64k/32k live truncation (`~/code/pi-long-horizon/src/thread-view/services/live-tool-result-truncation.ts`) — deliberately manual now, no auto-trigger.
**Mechanics (investigated 2026-07-04):** most machinery already exists. The boundary is a per-thread row; tail rendering already respects it (`render.ts` full-vs-abridged per tool result); the POC's thresholds survived as `DEFAULT_VISIBILITY = { maxTokens: 64000, targetTokens: 32000 }`; `status` already computes the zone. Pre-first-compact works free (boundary seeds 0, everything is tail — one code path, no thread-vs-view branching). Missing pieces: (1) an lhc `threadView` op — today compact is the boundary's only writer (`snapshot.ts` resets to compact point); the op walks tool results newest-first, accumulates to the target, sets the boundary behind that point, returns a receipt (old/new position, results shortened, tokens reclaimed). Deterministic, no inference, no schema change. Invariants: boundary only moves forward, never behind the compact point. (2) pi-lhc `/lhc-tool-prune` command + live session refresh (compact handler's rebuild path is the template). Optional arg overrides target tokens.
**Compact interaction:** none — verified compact's selection path never reads the boundary; compact just overwrites it at the end, absorbing any prior prune. Prune shrinks the visibility zone, so it can turn off a compact recommendation — intended. Later: the status notification should recommend prune vs compact as distinct reliefs.
**Cache shape:** matches the POC's hysteresis intent — one prefix invalidation per explicit prune, stable between runs. Per the standing ruling, the explicit command always executes (report, never refuse, when the zone is already under target).

### 30. Resume fidelity: first-session serving must character-match the DB reload
**What:** When a thread's first session is live, the context PI serves and what later reloads from the DB differ — extra markers and stray extras get stored in messages along the way, and the re-render on resume doesn't character-match what the live session was serving. That first resume then takes a big provider cache miss it shouldn't. Fix: tighten what gets stored/served in the initial session, strip the extras from stored messages, and build a proper diff test harness — capture the live session's rendered context, reload from the DB, diff to the character; any divergence is a defect. This is the plain-resume slice of item 27's byte-exact reload-fidelity requirement, pulled out because it hits every session resume today, not just future clone/fork. Relevant seams: `launcher/seed-session.ts`, `lifecycle/rehydrate.ts`, `serving/context.ts`, lhc's `getSessionThreadView`; `verify/replay.ts` is the closest existing scaffold.

## Deferred / later

### 23. Dialog band between smooth and detailed
**What:** A fifth band serving `pre_detailed_assembly` raw — dialog only (smoothed prompt + assistant text), no thinking, no tool calls, no compression. The smooth → detailed seam is currently a cliff: machinery strip, register flip (dialogue → third-person narrative), and compression all land in one step (~15–20% effective density drop). A dialog band splits it into two honest transformations: smooth → dialog drops machinery only; dialog → detailed does the register flip + compression. Cheap by construction: the artifact already exists as a stored derivation (it's the compression input, the failure floor, and the coverage-ladder degraded rung), so this is a selection/profile change — fifth band percentage + ladder entry — not pipeline work. Cost is the budget question: every point it gets comes from the other bands.

### 24. Post-brief horizon compression (level 2 chunks)
**What:** Content starts falling out of the brief band after ~1–2 weeks of real usage — beyond that horizon, turns have no representation at all. Add a compression tier past brief: compact chunks into something coarser (maybe level 2 chunks — chunks of chunks), so the oldest end degrades to a very cheap outcome-level narration instead of dropping out. Extends the band gradient's degrade-over-drop principle to the whole thread lifetime.

### 11. Tool-call/result derivation refinement (truncation holds the line)
**What:** Truncation at 500 chars stays in place for tool calls and results until this chunk. Then: study the headless open-source project's deterministic tool-output processing — get more done with deterministic techniques and reserve high-speed inference for key leverage points; per-tool/content-kind routing via the classifier — which still exists and is wired in (`messages/internal/classify-tool-result.ts`, called from `handlers.ts`), just bypassed while `FORCE_TOOL_RESULT_SUMMARY_FALLBACK = true` keeps everything on truncation, so this is re-enable-and-validate, not rebuild; evaluate re-introducing inference for tool activity only if quality AND speed prove out — last attempt clogged the durable work queue at intake-rate bursts. The Cerebras exploration (item 19) doubles as the feasibility probe: "provably drains at intake speed" is the bar.

### 22. Work-queue parallelism for message-level derivations
**What:** The queue drains one item at a time because dependencies between items aren't knowable in general. But message-level derivations (smoothing, tool-call/result summaries) are independent of each other by construction — the optimization from a prior planning session: pull ALL pending message work items at once and run their derivations in parallel. Not needed today (tool activity is truncation-only, so message-level inference volume is tiny), but it's the pressure-relief valve for drain backlog when item 11 re-introduces inference that fires on a large percentage of message events. Turn derivations stay sequential — not worth parallelizing, with one exception: a chunk's brief and detailed summaries can run concurrently. Sequence with item 11; the Cerebras probe (19/21) measures the other half of the same equation (per-call speed × parallelism = drain rate vs intake rate).

### 27. Thread clone + fork via file copy, with byte-exact reload fidelity
**What:** First-class `threads.clone` in lhc: checkpoint WAL → copy the sqlite file → stamp new threadId in `thread_metadata` → registry insert. Single-file threads make this near-free and — unlike the connector's current replay-based fork path (`lifecycle/fork.ts`) — the clone carries **all derivations with it**: no re-inference of the cascade, so forking a 300k-token thread costs the same as a 3k one and is byte-faithful to the source's state at fork time. Fork-from-earlier-point is the harder variant: truncate events past the fork point plus everything downstream (turns, chunk membership, derivations, view rows) as an SDK operation respecting intake's invariants — connector's job stays detection + pointing the new session at the clone. POC context: forking was hard there because thread state lived in two representations (database + rollout file) that had to fork in lockstep; one sqlite file removes the class.
**Connector follow-on (added 2026-07-03):** `/lhc-clone` command in pi-lhc riding the SDK op: copy the sqlite, stamp the new threadId, propagate it everywhere it lives (registry row, thread_metadata, connector state, PI thread entry). Open decision: after cloning, stay on the source thread, switch the live session to the clone, or prompt the user — default probably stay-with-notify, decide at build time.
**Clone-as-subagent (added 2026-07-03):** run a cloned thread as a subagent — clone the sqlite, launch a headless/child session seeded from the clone's view, get the warm-prompt-cache benefit of sharing the source thread's entire served prefix. Lee used this pattern in the POC era for cache economics. Hard dependency: item 30's character-exact resume fidelity must be locked first — the cache benefit only exists if the clone's served context is byte-identical to the source's live prefix; without that it's a full-price re-read and the feature is pointless.
**Reload fidelity (rigorous, to the character):** the served context after a reload/rehydrate/fork-seed must be **byte-identical** to what the live in-memory session was serving — suspicion on record: subtle differences on reload (whitespace, ordering, entry re-rendering drift) silently break provider prompt-cache prefixes, turning a warm 300k-token cache into a full-price re-read. Build the verification: capture the live session's rendered context, reload/clone, capture again, diff to the character; any divergence is a defect. `verify/replay.ts` is the existing seam closest to this.

### 28. Memory-index injection at context-rebuild boundaries (superseded framing ratified 2026-07-04)
**What:** Inject `memory/MEMORY.md` content into the served context so recall rides RL'd always-present-index behavior instead of an instructed read. Original framing (session-start-only injection, build against observed failure) superseded by ratified design: **refresh the injected index at every context rebuild — compact, prune, rehydrate — as part of the render, not a live fetch at serve time** (item 30's byte-exact reload discipline applies: the assembled view captures index content at rebuild time). Applies to both pi-lhc and cc-lhc.
**Why this shape (rulings, 2026-07-04):** (a) The agent's RL write-side reflexes are not cache-cost-sensitive — eager index writes are trained behavior, so mid-session re-render on every write would invalidate the prefix cache constantly; the design must absorb the cost, not the agent. (b) Rebuild boundaries are already full prefix invalidations, so refreshing there is marginally free. (c) No visibility gap: memories written before the last rebuild are in the injected index; memories written after are still in the live tail as authorship (the write actions themselves), right up until the next re-render migrates them into the index. Long-thread staleness (weeks, 100→1000 memories) is bounded by rebuild cadence, not thread lifetime. Lee ratified; the quiet-stretch degenerate case (weeks with no rebuild) dismissed as unrealistic — active weeks produce prunes/compacts.
**Interim step (cheaper, available now):** inline the index lines directly into AGENTS.md (killing MEMORY.md as a separate file, AGENTS.md self-describing) — deletes the instructed-read diligence link using existing injection. Not yet done; decide at implementation time whether to skip straight to the extension.
