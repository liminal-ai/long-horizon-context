Development narrative for LHC, compressed:

- **Start (June 3–4):** a fast prototype for an event-sourced thread system: events → messages → turns → chunks, with SQLite persistence, validation, triggers, and compression artifacts.
- **Epic 01 (June 10):** full rebuild into a rigorously tested SDK. Built thread creation/resolution, intake pipeline, message projection, turn state machine, and derivation work queue. This is where the core architecture became formal.
- **Epic 02:** added the derivation pipeline: prompt smoothing, tool-result summaries, turn rendering/composition, chunk summaries, edit/delete cascades, and a durable claim/lease work queue.
- **Epic 03:** introduced thread views and “smart compact” — the context-selection algorithm that assembles a token-budgeted prompt from detailed/brief/smoothed/tail bands.
- **Epic 04:** expanded read surfaces and proved lifecycle continuity end-to-end.
- **Epic 05:** integrated real inference via provider/model routing, prompt registry, failure classification, and real OpenRouter tests; also retired the CLI and made LHC SDK-only.
- **PI-LHC:** built the bridge into PI: session lifecycle, thread resolution, event capture, replay verification, and fail-closed hook integration.
- **Epic 07:** major architecture realignment, naming cleanup, workspace/tooling overhaul, and derivation “dial-in” work to tune summaries and compression.
- **Late June:** extensive comment cleanup, context-serving integration for PI, Smart Compact v2, and compact-floor/coverage fixes.
- **HEAD:** production polish: removed old specs/artifacts, tightened logging/auth, updated workspace files, and upgraded PI compatibility.

**Big arcs:**
1. Prototype → formal SDK
2. Derivation pipeline → smart context serving
3. Test-double framework → real model inference
4. Internal tool → PI extension integration
5. Heavy scaffolding/docs → cleaner production codebase

# Shared-Tech Machinery: Complete Analysis

## 1. Durable Work Queue (`work-queue/index.ts`) — 800+ lines

### The Item Lifecycle

A work item moves through: **queued → claimed → (done | retried-to-queued | failed_terminal)**

**Enqueue** — `enqueue(transaction, input)`:
- Generates a deterministic ID: `w-${sourceId}-${kind}-v${sourceVersion}`. This means re-queueing the same source at the same version generates the same ID (dedup), while a post-mutation replacement at a bumped version never collides.
- Inserts the `work_item` row with status `queued`.
- Upserts the `derivation` row(s) to `pending` state — this is the **only place** derivation rows are created. Completion only UPDATEs; it never inserts.
- Registers a post-commit hook that pokes the scheduler.

**Claim** — `claimNext(db, now, leaseDurationMs)`:
- One atomic `UPDATE...RETURNING` under `BEGIN IMMEDIATE` — no read-then-write gap.
- Only the **head row** (oldest by `rowid`) is considered. The queue is strictly FIFO — no skip-ahead.
- Claimable if: `status = 'queued' AND eligible_at <= now` OR `status = 'claimed' AND claim_expires_at <= now` (expired lease reclaim).
- On claim: `status → 'claimed'`, `claim_epoch += 1`, `claim_expires_at` set. If reclaiming an expired claimed row, `attempts += 1` (a crash is visible in the report and counts against retry budget).
- Returns `ClaimOutcome`: `"claimed"` with the item, `"empty"` (no rows), `"in_flight"` (head has live lease), `"waiting"` (head is backing off).

### Epoch Fencing

The `claim_epoch` column is the core coordination mechanism:
- Every claim increments `claim_epoch`.
- Every completion/retry/terminal operation checks `WHERE work_item_id = ? AND status = 'claimed' AND claim_epoch = ?`.
- If a lease expires and another process reclaims the item, the epoch increments. The original claimant's completion write misses (epoch mismatch) → `lost_lease`, meaning stale work is discarded silently with no data corruption.
- This makes cross-process safety rely on **durable rows alone** — no in-memory coordination needed.

### Completion — `complete(db, item, writes, derivedAt, onApplied?)`:
- Under `BEGIN IMMEDIATE`: verify ownership (epoch check), assert exact derivation writes match expected targets (via `assertExactDerivationWrites` — no missing, no extra, no duplicates), UPDATE derivation rows to `ready` with version check (`source_version = ?`), delete the work item, run `onApplied` hook, commit.
- If all derivation UPDATEs hit zero rows (source version moved since enqueue): `stale_discarded`. The mutation cascade already re-queued at the new version.
- A partial hit (some matched, some didn't): `DerivationCompletionError` — state corruption.

### Retry and Terminal Failure

**`retryClaimedItem`** — Returns item to `queued` with `attempts += 1`, `eligible_at` set to backoff time, `claimed_at/claim_expires_at` cleared. Epoch-checked.

**`failTerminal`** — UPDATE derivation rows to `failed` or `blocked`, copy `attempts` and `lastError` into derivation metadata (the queue is not an audit table — durable outcome detail lives on the derivation row), delete the work item. Version-checked so stale terminal failures don't stamp rebuilt derivations.

**`failAttempt`** — The combined retry/terminal decision: if retryable and under budget, retry with exponential backoff (`min(base × 2^attempts, cap)`). Otherwise, terminal.

### Supersede — `supersedeQueued(db, targets)`:
Deletes queued items for given (kind, sourceRef) pairs. Used by the mutation cascade to clean up obsoleted work before re-enqueueing at the next source version. Claimed items are left alone — their stale completions are caught by the version check.

### `createOrClaimImmediateWorkItem` — Synchronous derive path
For `turns.deriveTurn` and similar synchronous derive calls: creates or claims a work item in one transaction, checking derivation boundaries match expected state. If live work exists for the same source/version, returns `in_flight`. Otherwise creates the item and immediately claims it.

## 3. Scheduler (`scheduler.ts`) — 350+ lines

### Two Modes
- **Manual**: poke/touch are no-ops. Drain is only manual (`work.drain(ref)`).
- **Background**: per-thread single-flight drain with pending-flag coalescing.

### Background Scheduling Mechanics
Per-thread state: `{ running, pending, passes, waiters, wakeTimer }`.

**Poke** (post-commit nudge that work was queued):
1. Clear any pending wake timer.
2. If a drain is already running for this thread → set `pending = true` (burst coalesce: at most one further pass).
3. If not running → start `runLoop`.

**`runLoop`**:
1. Defers to next macrotask (so the committing operation's synchronous tail finishes first — the drain never contends with the transaction that scheduled it).
2. Loops: clear pending flag, increment passes, `runDrain(filePath, deps)`, repeat while pending.
3. On exit: if the last report stopped on `"waiting"` or `"in_flight"`, arm a wake timer.
4. Otherwise, flush waiters (drainSettled resolvers).

**Touch** (thread-file open announcement):
1. Learn threadId → filePath mapping.
2. On first touch per process lifetime: check for leftover live work and schedule catch-up.

**Wake Timer**:
- At most one per thread, `unref()`'d so it never keeps the process alive.
- Armed when a drain stops on retry backoff (`eligible_at`) or unexpired claim (`claim_expires_at`).
- On fire: re-enters the poke path → claimNext re-reads the head.

**`drainSettled(threadId)`**:
- Returns a Promise that resolves when no drain is running, no drain is pending, AND no wake timer is armed.
- A pending wake counts as unsettled: the retry it will fire is part of the drain cycle.

### Instance Isolation
The `InstanceSeam` + `AsyncLocalStorage` pattern means multiple SDK instances in one process each have their own scheduler. `scopeSurface` wraps every domain operation in `runWithInstanceSeam(seam, ...)` so deep poke/touch calls reach this SDK's scheduler. A manual SDK's operations run with a no-op seam → can never accidentally trigger a background SDK's drain.

## 4. Inference Adapter (`inference-adapter.ts`)

### The Pipeline
`createInferenceCallbacks(config)` returns the same 4-operation `InferenceCallbacks` interface that direct injection provides. Every operation follows:

1. **Look up assignment** for the derivation kind (provider, model, prompt name, thinking level, target ratios).
2. **Resolve prompt template** from `PROMPT_REGISTRY` by the assignment's prompt name.
3. **Merge target ratios** from the assignment into the prompt's render input.
4. **Render the prompt** — the template produces `{ role: "system"|"user", content: string }[]` messages.
5. **Bound input** — for tool results, `boundContent(content, maxInputChars)` truncates huge content to head+tail around a marker.
6. **Call host** via `safeCall(config.call, input, timeoutMs)` — try/catch + timeout race.
7. **Shape output** — trim whitespace; empty/whitespace-only → `empty_output` classified failure (retryable).
8. **Stamp provenance** — `{ provider, model, prompt }` from config, never from model output.

### Failure Classification (`classify.ts`)
Pure table:
| Kind | Retryable |
|------|-----------|
| `rate_limit` | ✓ |
| `timeout` | ✓ |
| `network` | ✓ |
| `empty_output` | ✓ |
| `other` | ✓ |
| `auth` | ✗ |
| `invalid_request` | ✗ |

**`safeCall`** — Wraps the host's `ModelCall` in:
1. A try/catch that classifies thrown exceptions as `{ kind: "other" }`.
2. A `Promise.race` against a timeout that classifies as `{ kind: "timeout" }`.
3. So host behavior can never crash a drain.

### Routing
Per-kind assignment controls routing: each derivation type can use a different provider/model/prompt. The 4 callback methods map to derivation types:
- `smoothPrompt` → `"smoothed_prompt"` assignment
- `summarizeToolResult` → `"tool_result_summary"` assignment
- `compressDetailedTurn` → `"detailed_turn_compression"` assignment
- `summarizeChunkBrief` → `"chunk_summary_brief"` assignment

## 8. Persistence (`persist.ts`)

### `createDbReadTransaction(threadRef, operation)`
1. Runs under `runWithThreadTouchSuppressed` (reads never trigger scheduler catch-up).
2. Resolves threadRef to filePath (via registry for threadId refs).
3. Opens thread database (validates, migrates).
4. `BEGIN` → read threadId → run operation → `COMMIT`.
5. Always closes db in finally.

### `createDbWriteTransaction(threadRef, operation, clock?)`
1. Resolves threadRef, opens database.
2. Reads threadId.
3. `BEGIN IMMEDIATE` → run operation (provides `DbWriteTransaction` with db, filePath, threadId, clock, postCommitHook, poke) → `COMMIT`.
4. Flushes post-commit hooks after COMMIT.
5. Always closes db in finally.

The `DbWriteTransaction` object carries everything the operation needs: the live db handle, the resolved poke target (from `resolveInstancePoke`), and a post-commit hook set.

### AsyncLocalStorage-based SDK scoping

### Fallback Path
Below-SDK direct domain calls (test utilities, single-background default path) fall through to module-global slots:

`runWithThreadTouchSuppressed(operation)` — wraps the operation with `touch: () => {}`. All read transactions use this so opening a thread file for a read can never trigger scheduler catch-up.

# PI-LHC Connector: Complete Architecture

## Overview

The `pi-lhc` package is a **PI extension** that bridges the PI coding agent harness with the LHC context management SDK. It has four main responsibilities:

1. **Capture** — Record PI session events into LHC's durable thread
2. **Compact** — Intercept PI's compaction requests and run LHC smart compact instead
3. **Serve** — Load LHC thread-view content into PI sessions (context hydration)
4. **Lifecycle** — Manage thread creation/resolution/forking across PI session boundaries

---

## 1. Extension Entry (`index.ts`) — The Hook Rail (~800 lines)

### `createConnector(deps)` → `Connector`

The factory builds a closure-based connector with mutable state held in the closure (never module-level):

**Closure state:**
- `state: SessionState | null` — Plain-data thread reference + flags + health. Structurally cannot hold a PI ctx.
- `instance: LhcInstance | null` — Live SDK engine (sdk + threadRef + dispose). Rebuilt per session.
- `captureSession: CaptureSession | null` — PI session id, TurnAccumulator, sourceSeq counter, pending messages.
- `pendingFork: PendingFork | null` — Fork info captured from `session_before_fork`.
- `compactDiagnostics` — Buffer of compact cancel diagnostics.

### Hook Registration

`connector.register(pi)` registers handlers for all hooks:

**Epic 1 hooks (capture):** `session_start`, `message_end`, `turn_end`, `agent_end`, `model_select`, `thinking_level_select`, `session_before_fork`, `session_before_switch`, `session_shutdown`.

**Compact hooks:** `session_before_compact`, `session_compact`.

**Commands:** `/lhc-rehydrate`, `/lhc-dump-view`.

**Flags:** `--lhc-thread`, `--lhc-resume`, `--lhc-continue`.

### Session Start Flow

`onSessionStart` resolves the thread through a priority cascade:

1. **Fork path** — If `pendingFork` (from `session_before_fork` hook) or detected from session tree, create a new thread, seed it by replaying source events up to fork point.
2. **Launcher-owned startup** — If the `pi-lhc` binary resolved the thread before PI session creation, use that thread (no re-resolution).
3. **Pre-attached thread entry** — If a `pi-lhc.thread` custom entry exists in the PI session, re-resolve that threadId.
4. **Normal launch** — Read launch flags (`--lhc-thread`/`--lhc-resume`/`--lhc-continue`/none), resolve through registry.

After resolution: init the LHC instance in background mode, create `SessionState`, write a durable `pi-lhc.thread` entry to PI's session, create the `CaptureSession`, run startup validation (probe inference assignments against PI's model registry).

### Message Capture Flow

`onMessageEnd(event, ctx)`:
1. Find or create the PI session entry's id for the message.
2. Call `mapMessage(event.message, mapCtx)` → ordered LHC `MessageEventInput[]`.
3. Feed events through `TurnAccumulator.onMessage()` to track open-turn state.
4. Batch captured events and flush to `capture(events, instance)` → `intakeStream.messageEvents`.

`onAgentEnd(event, ctx)`:
1. Flush all pending messages.
2. Emit `TurnAccumulator.onAgentEnd()` → `[turn_end]` if a turn is open.
3. Capture the turn_end event.

**Key design rule:** ONE LHC turn per user exchange. PI's per-step `turn_end` (which fires on every turnIndex) is explicitly **not** used as a turn boundary. Only `agent_end` closes the LHC turn.

### Dispose Flow

`onDispose` (session_before_switch, session_shutdown):
1. Flush pending messages.
2. `disposeInstance(instance, { settle })` → await `drainSettled` (unless headless quit).
3. Clear captureSession, compactDiagnostics.

## 2. Capture Subsystem (`capture/`)

### `map-message.ts` — PI Message → LHC Events

Pure mapping function `mapMessage(msg, ctx) → MessageEventInput[]`:

- **User message:** → `user_prompt` (text parts) + `runtime_note` (unsupported parts like images/fileRefs)
- **Assistant message:** → `assistant_thinking` → `assistant_text` → `tool_call` (per call), in PI's confirmed part order. Aborted messages get a trailing `runtime_note` with the disposition.
- **Tool result:** → `tool_result` correlated by `toolCallId`, carrying `isError`.
- Empty messages → `runtime_note` ("message omitted: no mappable content parts"). Never silently dropped.

### `idempotency.ts` — Stable Event Keys

4-tier precedence for idempotency key construction:
1. **PI entry id** (most stable — real finalized message)
2. **toolCallId** (stable across re-delivery, independent of order)
3. **responseId** (stable per assistant response)
4. **Content fingerprint** (last resort — sha256-based)

Each tier disambiguates with `blockIndex` and `kind` for fan-out. The scheme makes crash-replay safe (same logical event → same key → dedup skip).

### `turn-accumulator.ts` — LHC Turn Boundary

Simple state machine: opens on `user_prompt`, emits `turn_end` only at `agent_end`. PI's per-step `turn_end` is deliberately ignored. A hard kill leaves the turn open (tolerated on reattach).

### `runtime-changes.ts` — Model/Thinking Level Events

`mapModelSelect` → `model_change` event. `mapThinkingLevelSelect` → `thinking_level_change` event. Both use the same idempotency key scheme.

### `converter.ts` — Isolated Flush

`capture(events, instance)` wraps `intakeStream.messageEvents` with:
- Total isolation: even if the thread file throws, it returns an OpResult.
- On `invalid_event`: records a durable gap (a `runtime_note` with a fingerprinted key so re-delivery dedups).
- On store unavailable: surfaces the failure for health reporting (no durable gap possible).

## 3. Compact Subsystem (`compact/`)

### `handler.ts` — `handleSessionBeforeCompact`

PI fires `session_before_compact` when context needs compaction. The handler:

1. **Preconditions:** Check active thread + instance exist, flush pending capture, check no capture failure.
2. **Floor gate:** Read serving context tokens; if below `COMPACT_FLOOR_TOKENS` (50k), cancel — "nothing to reclaim."
3. **Preview:** Call `threadView.previewCompact` with LHC's `DEFAULT_COMPACT_PROFILE`. If no new bands would be produced, cancel.
4. **Map first-kept message:** Convert LHC's `firstKeptMessageId` to a PI session entry id (needed for PI's compaction protocol). This uses the `SessionThreadView` + seed-entry-map for messages seeded from a prior LHC view.
5. **Compact:** Call `threadView.compact` → get `CompactReceipt` with rendered bands.
6. **Assemble result:** Build PI's `CompactionResult` with summary text (band text joined with `[context · band]` headers), firstKeptEntryId, tokensBefore.

Returns `{ compaction }` on success, `{ cancel: true }` on any failure (with diagnostic buffered).

### `profile.ts` — Compact Configuration

```
DEFAULT_COMPACT_PROFILE: lowerBound=120k, full=25%, smooth=35%, detailed=20%, brief=20%
COMPACT_FLOOR_TOKENS: 50k
```

Band sum validated at module load (static assertion).

### `result-mapping.ts` — PI Entry ID Mapping

`mapFirstKeptToEntryId` resolves LHC's `firstKeptMessageId` (an LHC message id like `m42`) to a PI session entry id:

1. **Live tier:** Find the message's source in `SessionThreadView`, parse the idempotency key to extract the PI entry id, verify it exists in the compact branch entries.
2. **Seed tier:** Check the `LhcSeedEntryMap` (written when the session was seeded from an LHC view) for a direct lhcMessageId → piEntryId mapping.

### `seed-entry-map.ts` — Compact Continuity

When a PI session is seeded from LHC, a `pi-lhc.seed-entry-map` custom entry is written recording `{ lhcMessageId, piEntryId }` pairs. This mapping enables compact to find the PI-side entry id for messages that originated from a prior LHC view (not captured live in this session).

### `diagnostics.ts` — Compact Cancel Tracking

Buffers cancel diagnostics, writes warning logs, notifies via UI. Cleared on session boundary and successful compact.

### Context Serving Architecture

Context is **not** served via PI's `context` hook. Instead:

1. **Launcher path:** The `pi-lhc` binary resolves the thread, reads `getSessionThreadView`, and seeds an in-memory PI session before PI starts. The connector's `session_start` finds the `LauncherOwnedStartup` and uses the pre-resolved thread.

2. **Rehydrate path:** The `/lhc-rehydrate` command creates a new PI session, seeding it from the current LHC thread view. This replaces the PI session's content with the latest compacted view.

3. **Compact path:** When PI requests compaction, the connector runs LHC smart compact and returns the result to PI through the `session_before_compact` return value, which PI uses to rewrite its session.

## Cross-Cutting Design Principles

1. **Never retain PI ctx** — The connector holds only plain data (`SessionState`) and its own engine (`LhcInstance`). PI replaces ctx on every hook call; a stale reference throws.

2. **Fail-closed capture** — Every capture failure returns an OpResult, never throws into a PI hook. Malformed events record durable gaps; store-unavailable failures surface as health diagnostics.

3. **One LHC turn per user exchange** — PI's per-step `turn_end`/`turnIndex` is explicitly not used as a boundary. The accumulator closes turns only at `agent_end`.

4. **Context via session seeding, not the context hook** — The connector does NOT register a `context` hook. Instead, the launcher seeds an in-memory PI session from `getSessionThreadView` before PI starts, and rehydration replaces the session at command time.

5. **Dynamic pi-ai loading** — `@earendil-works/pi-ai` is loaded at runtime via dynamic import so the package works without a build-time dependency.

6. **Compact floor gate** — Compact is refused below 50k serving tokens to avoid creating useless snapshots on small threads.

# Deep Dive: The Four Trickiest Internals

## 1. Work Queue Claim/Epoch Fencing — The Concurrency Design

### The Three-Phase Pattern

Every work item processed by the drain follows a three-phase pattern where **no SQLite transaction spans the handler execution**:

```
Phase 1: BEGIN IMMEDIATE → claim (UPDATE+RETURNING) → COMMIT
Phase 2: handler runs (no open transaction — can take seconds for inference)  
Phase 3: BEGIN IMMEDIATE → complete/retry/terminal (with epoch check) → COMMIT
```

This is the core design decision. If the transaction spanned the handler, an inference call taking 30 seconds would hold a SQLite write lock for 30 seconds, blocking all other operations on the thread file. Instead, the handler runs "loose" and the completion phase re-validates ownership.

### How Epoch Fencing Prevents Corruption

The `claim_epoch` column is an integer that starts at 0 and increments on every claim. The race it prevents:

```
Process A: claimNext() → gets item X at epoch=1, starts handler
Process A: handler takes 3 minutes (inference hangs)
Process B: claimNext() → lease expired, reclaims item X at epoch=2, starts handler
Process B: handler completes, complete() → WHERE claim_epoch=2 → succeeds, deletes item
Process A: handler finally returns, complete() → WHERE claim_epoch=1 → 0 rows changed → "lost_lease"
```

Without epoch fencing, Process A's stale completion would write to derivation rows that Process B already wrote. With it, the stale write harmlessly misses.

### The claimNext SQL — One Atomic UPDATE

The claim is a single `UPDATE...WHERE...RETURNING` statement, not a `SELECT` followed by an `UPDATE`. This is critical — a read-then-write would have a race window where two processes read the same head and both claim it. The SQL:

```sql
UPDATE work_item SET status = 'claimed', claimed_at = ?, claim_expires_at = ?,
   claim_epoch = claim_epoch + 1,
   attempts = attempts + CASE WHEN status = 'claimed' THEN 1 ELSE 0 END
 WHERE work_item_id = (
   SELECT work_item_id FROM (
     SELECT work_item_id, status, eligible_at, claim_expires_at
     FROM work_item WHERE status IN ('queued', 'claimed')
     ORDER BY rowid LIMIT 1
   )
   WHERE (status = 'queued' AND (eligible_at IS NULL OR eligible_at <= ?))
      OR (status = 'claimed' AND (
        claim_expires_at IS NULL OR unixepoch(claim_expires_at) IS NULL OR claim_expires_at <= ?
      ))
 )
 RETURNING ...
```

The nested subqueries work like this:
1. **Inner SELECT**: Find the oldest live row by `rowid` (insertion order = FIFO).
2. **Outer WHERE**: Only claim it if it's actually claimable — either queued with eligible_at past, or claimed with expired lease.
3. **UPDATE**: If the WHERE matches, atomically set claimed + bump epoch + conditionally bump attempts.
4. **RETURNING**: Give back the claimed row's data so no second read is needed.

The `CASE WHEN status = 'claimed' THEN 1 ELSE 0 END` on `attempts` is subtle: when reclaiming an expired lease (the previous claimant died), it increments attempts so the crash is counted against the retry budget. A normal claim from `queued` doesn't touch attempts (the handler hasn't run yet).

### The Head-First / No-Skip-Ahead Rule

When claimNext fails to claim, it re-reads the head **inside the same BEGIN IMMEDIATE** to classify why:
- Head is `claimed` with a live lease → `"in_flight"` (someone else is working on it)
- Head is `queued` with `eligible_at` in the future → `"waiting"` (backing off after a retry)
- No live rows → `"empty"`

This is why the queue is strictly FIFO: a row with a future `eligible_at` blocks everything behind it. Work is never reordered. The scheduler uses the `waitingUntil` / `claimExpiresAt` from these outcomes to arm wake timers.

### Source-Version Check in Completion

The completion `UPDATE derivation SET state = 'ready' ... WHERE source_version = ?` is the second concurrency guard. Scenario:

```
1. Message m5 is recorded, smoothed_prompt derivation created at version 1
2. Work item queued for smoothed_prompt at version 1
3. User edits m5 → cascade bumps derivation to version 2, new work queued at version 2
4. Old version-1 handler finishes, tries to complete → WHERE source_version = 1 → 0 rows (it's now version 2)
5. Result: "stale_discarded" — the stale content is silently dropped
```

The three-way state: `hits` (matched and updated), `misses` (didn't match), `stale` (all missed). A partial hit (some matched, some didn't) is a `DerivationCompletionError` — state corruption, because a single work item's derivation targets should all be at the same version.

### The `supersedeQueued` Function

During a cascade, still-queued items for superseded work are `DELETE`d from `work_item`. But **claimed** items are deliberately left alone — their epoch-fenced completion will just miss (source version moved) and report `stale_discarded`. Trying to delete a claimed item would race with the handler.

## 2. The Mutation Cascade — Tracing a Message Edit End-to-End

### Setup: The State Before the Edit

Imagine message `m5` is a `user_prompt` in turn `t3`. Turn `t3` is closed and placed in chunk `c2`. The derivation state is:

```
message/m5/smoothed_prompt       → ready, version 1, content="smoothed text"
turn/t3/turn_rendering           → ready, version 1
turn/t3/pre_detailed_assembly    → ready, version 1  
turn/t3/detailed_turn_compression → ready, version 1
chunk/c2/chunk_summary_detailed  → ready, version 1
chunk/c2/chunk_summary_brief     → ready, version 1
```

### Step 1: Entry validation (`messages.edit`)

```typescript
const target = readMutableMessage(transaction.db, edit.messageId);
```

This reads message `m5` joined to its turn via `LEFT JOIN turns t ON t.turn_id = m.turn_id`, filtered by `m.deleted_at IS NULL`. It checks:
- Message exists and is not deleted → otherwise `message_not_found`
- Turn status is `closed` → otherwise `turn_open` (open-turn messages can't be edited)
- NOT the first live member of the turn → that check is for delete only (initiates-turn protection)

### Step 2: Content update (`applyMessageEdit`)

Updates each block's content-bearing field (`text` for text blocks, `content` for tool_result, etc.) and re-stamps the `token_estimate` using the same `estimateTokens` function. Events are never touched.

### Step 3: The cascade (`cascadeFromMessage`)

```typescript
const cascade = cascadeFromMessage(transaction, edit.messageId);
```

#### 3a: Chain walk (`chainSubjects`)

Walks upward from the edited message:
1. `{ subjectKind: "message", subjectId: "m5" }` — the message itself
2. Read `message.turn_id` → `t3` → `{ subjectKind: "turn", subjectId: "t3" }`
3. Read `chunk_member WHERE turn_id = 't3'` → `c2` → `{ subjectKind: "chunk", subjectId: "c2" }`

Result: `[message/m5, turn/t3, chunk/c2]`

#### 3b: Counterpart lookup (`pairedCounterpartSubject`)

Since m5 is a `user_prompt`, its blocks are `text` type, not `tool_call`/`tool_result`. The query for a paired block returns `undefined`. No counterpart is added.

(If m5 were a `tool_result`, this would find the `tool_call` sharing the same `toolCallId` — the other half of the pair — and add it to the clear set so its summary gets rebuilt too.)

#### 3c: Core cascade (`runCascade`)

For an edit, everything is in the `clearSubjects` list (nothing dropped). The cascade:

**Phase 1: Read existing derivation rows**

For each subject in `[message/m5, turn/t3, chunk/c2]`, read all derivation rows:
- `message/m5` → `smoothed_prompt` at version 1
- `turn/t3` → `turn_rendering` at v1, `pre_detailed_assembly` at v1, `detailed_turn_compression` at v1
- `chunk/c2` → `chunk_summary_detailed` at v1, `chunk_summary_brief` at v1

**Phase 2: Group by rebuild kind**

The `DERIVATION_REBUILD_KINDS` map tells us which work kind rebuilds each derivation:
- `smoothed_prompt` → `prompt_smoothing` (message-owned)
- `turn_rendering` → `turn_derivation` ← same kind
- `pre_detailed_assembly` → `turn_derivation` ← same kind (grouped!)
- `detailed_turn_compression` → `detailed_turn_compression`
- `chunk_summary_detailed` → `chunk_summary_detailed`
- `chunk_summary_brief` → `chunk_summary_brief`

This produces 5 `RebuildGroup`s:

| Group key | Kind | Derivations | maxSourceVersion |
|---|---|---|---|
| `message:m5:prompt_smoothing` | `prompt_smoothing` | `[message/m5/smoothed_prompt]` | 1 |
| `turn:t3:turn_derivation` | `turn_derivation` | `[turn/t3/turn_rendering, turn/t3/pre_detailed_assembly]` | 1 |
| `turn:t3:detailed_turn_compression` | `detailed_turn_compression` | `[turn/t3/detailed_turn_compression]` | 1 |
| `chunk:c2:chunk_summary_detailed` | `chunk_summary_detailed` | `[chunk/c2/chunk_summary_detailed]` | 1 |
| `chunk:c2:chunk_summary_brief` | `chunk_summary_brief` | `[chunk/c2/chunk_summary_brief]` | 1 |

**Phase 3: Supersede old queued work**

```typescript
const superseded = supersedeQueued(transaction.db, [...supersedeTargets, ...groupTargets]);
```

Deletes any still-queued items for these (kind, sourceRef) pairs. Since the derivations were all `ready`, there are probably no queued items. But if there were (e.g., a retry was pending), they'd be deleted here — before the replacement enqueues, so the deterministic work item IDs (which include the version number) can't collide.

**Phase 4: Enqueue replacement work**

Sorted by `REBUILD_KIND_ORDER` (prompt_smoothing=0, turn_derivation=2, detailed_turn_compression=3, chunk_summary_detailed=4, chunk_summary_brief=5), each group enqueues one work item at `maxSourceVersion + 1 = 2`:

```
w-m5-prompt_smoothing-v2        → derivations: [message/m5/smoothed_prompt]
w-t3-turn_derivation-v2         → derivations: [turn/t3/turn_rendering, turn/t3/pre_detailed_assembly]
w-t3-detailed_turn_compression-v2 → derivations: [turn/t3/detailed_turn_compression]
w-c2-chunk_summary_detailed-v2  → derivations: [chunk/c2/chunk_summary_detailed]
w-c2-chunk_summary_brief-v2     → derivations: [chunk/c2/chunk_summary_brief]
```

Each `enqueue` call UPSERTs the derivation row to `pending` at the new version:

```sql
INSERT INTO derivation (...) VALUES (?, ?, ?, 'pending', 2)
ON CONFLICT (...) DO UPDATE SET
  state = 'pending', content = NULL, reason = NULL, metadata = NULL,
  gaps = NULL, derived_at = NULL, source_version = 2
```

This atomically erases the old `ready` content and stamps version 2. Each enqueue also registers a post-commit poke.

### Step 4: Return to caller

The `MutationResult` reports:
- `changed`: `{ messageIds: ["m5"], turnIds: [] }`
- `cleared`: all 6 derivations
- `dropped`: empty (edit doesn't drop anything)
- `queued`: the 5 work items
- `superseded`: any old queued items that were deleted

### Step 5: Transaction COMMIT and post-commit

The entire edit — content update, derivation resets, old-item supersedes, new-item enqueues — committed atomically. After COMMIT, post-commit hooks fire: pokes reach the background scheduler, which schedules drains for the thread.

### Step 6: Background drain processes the replacement work

The scheduler picks up the queued items in FIFO order. The `prompt_smoothing` item runs first (it was enqueued first by insertion order). The handler re-reads `m5`'s new content, calls inference, and the completion writes `smoothed_prompt` to `ready` at version 2.

Then `turn_derivation` runs — it re-reads `t3`'s member messages (including `m5`'s new derivation), composes fresh turn_rendering + pre_detailed_assembly, and in its `onApplied` hook, places the turn and enqueues `detailed_turn_compression`.

And so on up the chain. The dependency ordering means each handler reads the latest content from its inputs.

## 3. The Compact Selection Algorithm — The Pure Walk

### Two Halves by Design

The algorithm is split into `readSelectionInputs` (IO + corruption check) and `selectArrangement` (pure function). This split means:

1. Corruption (referential damage, multiple open turns) is caught before any write transaction opens, so the prior view stays intact.
2. The selection is deterministic: same inputs → same arrangement, testable with goldens.

### Corruption Checks in `readSelectionInputs`

Three kinds of canonical damage are detected:
- **Multiple open turns**: `throw CanonicalCorruptionError("turn_state_corrupt", ...)` — the compacted span can't be identified if we don't know which turn is open.
- **Closed turn with no close boundary**: A closed turn must have `closedAtEventOrder` — without it, the compact point can't snap to turn boundaries.
- **Orphan references**: A message referencing a missing turn, or a chunk member referencing a missing turn. Note: **tombstoned turns are legitimate reference targets** — the `turnIds` set includes all turns (including deleted), so a chunk member pointing at a deleted turn passes the referential check. The selection walk itself filters deleted turns out via the `!row.deleted` filter.

### Compact Point Calculation (Rule 1)

Walk messages **newest-first**, summing token estimates until the sum reaches the `full` band budget (e.g., 25% of 120k = 30k). The crossing message is the one that pushed the sum over.

**The snap**: The compact point must land on a turn boundary, so the tail never begins mid-turn. Two cases for the crossing message:

1. **Message is in an open turn**: Open-turn messages are always tail. Snap the compact point to the previous closed turn's `closedAt`. All open-turn content stays in the tail.

2. **Message is in a closed turn, at or before the turn's start**: The full budget covers this turn entirely → the compact point moves to the previous closed turn's `closedAt` (this turn becomes tail).

3. **Message is in a closed turn, after the turn's start**: The budget only partially covers this turn → snap **forward** to this turn's `closedAt`. The partially-covered turn falls **whole** to the bands, not to the tail. This is the subtle case: the algorithm prefers giving the bands a complete turn over leaving a partial turn in the tail.

If the budget is never reached, `compactPoint = 0` — everything stays as tail, no bands are produced.

### Band Filling (Rules 2–4)

**Smooth** (Rule 2): Take all closed turns wholly behind the compact point (`closedAt <= compactPoint`). These are the "banded turns." Fill newest-first against the smooth budget using `buildTurnEntry`, which resolves `detailed_turn_compression` content (or degrades through fallback ladders). Track `oldestSmoothOrder` — the oldest turn included in smooth.

**Chunk candidacy** (Rule 3–4 prep): A closed chunk is a candidate for detailed/brief only if its **newest live member turn** is (a) a banded turn AND (b) older than `oldestSmoothOrder`. This prevents overlap: chunks overlapping the smooth band would double-represent content.

**Detailed** (Rule 3): Fill newest-first from chunk candidates against the detailed budget, building entries from `chunk_summary_detailed` content.

**Brief** (Rule 4): Fill newest-first from the remaining chunks (after detailed consumed its share) against the brief budget, using `chunk_summary_brief` content.

### The `fillBand` Function — The Shared Fill Rule

```typescript
function fillBand<T>(candidates: T[], bandBudget: number, build: (c: T) => ArrangementEntry) {
  const included = [];
  let sum = 0;
  for (let i = 0; i < candidates.length; i++) {
    const entry = build(candidates[i]);
    if (sum + entry.tokens <= bandBudget) {  // <= inclusion: exactly filling is included
      included.push(entry); sum += entry.tokens;
      continue;
    }
    if (included.length === 0) {  // first entry over budget → include anyway (never empty a band if material exists)
      included.push(entry);
      return { included, rest: candidates.slice(i + 1) };
    }
    return { included, rest: candidates.slice(i) };  // crossing entry stops the band, not included
  }
  return { included, rest: [] };
}
```

Key behaviors:
- `<=` threshold: an entry exactly filling the budget is included.
- First-entry guarantee: if the very first candidate exceeds the budget, it's included anyway so a band is never empty when material exists. But only that one entry.
- The rest array carries unconsumed candidates to the next band (detailed → brief).

### Coverage Entries — The Gap Filler

After smooth/detailed/brief selection, there's a coverage invariant: **every closed turn behind the compact point must be represented** — either directly selected in smooth, or covered by a selected chunk's membership. If a turn falls through the cracks (typically because its chunk is still open and thus not a candidate), it gets a **coverage entry**.

The coverage check:
1. Build `coveredTurnIds` — turns explicitly selected in smooth, plus all banded turn members of selected chunks.
2. Find `oldestSelectedTurnOrder` — the oldest turn anywhere in the selection.
3. Any banded turn at or newer than `oldestSelectedTurnOrder` that isn't in `coveredTurnIds` gets a coverage entry.

The coverage entries use a three-tier degradation:
1. `detailed_turn_compression` is ready → use it (not degraded)
2. `pre_detailed_assembly` is ready → use it (degraded=true, marked as coverage-from-pre-detailed-assembly)
3. Neither ready → gap entry (gap=true, reason explains what's missing)

Coverage entries are placed in the **detailed** band and sorted by record order alongside normal detailed entries. This means the detailed band can have both chunk-level entries and individual turn-level coverage entries interleaved by time.

### Final Assembly Order

```typescript
entries = [
  ...brief.included.sort(byRecordOrder),          // oldest→newest within brief
  ...[...detailed.included, ...coverageGaps].sort(byRecordOrder),  // oldest→newest within detailed
  ...smooth.included.sort(byRecordOrder),          // oldest→newest within smooth
]
```

This is gradient order: brief (oldest/most compressed) → detailed → smooth (newest/least compressed) → then tail (appended at serving time). Within each band, entries are oldest-first by `startOrder`.

## 4. Thread Migration — The Rename-and-Rewire Problem

### The Three Schema Versions

**Version 1 → 2**: Add the `derivation_log` table (append-only inference execution history). Straightforward DDL: `CREATE TABLE IF NOT EXISTS derivation_log ...` + two indexes.

**Version 2 → 3**: The tricky one — rename `smooth_turn_compression` to `detailed_turn_compression` across the **entire database**. This happened because the derivation type was renamed during Epic 07's architecture realignment.

### The Rename Cascade (`migrateDetailedTurnCompressionRename`)

The rename must touch **every table** that stores the derivation type string:

1. **`derivation` table**: `UPDATE derivation SET derivation_type = ? WHERE derivation_type = ?` — the primary data.
2. **`derivation_log` table**: Same pattern for the execution history.
3. **`log` table**: The operational log's `derivation_type` column.
4. **`derivation.metadata` JSON**: The prompt name embedded in metadata JSON (`"prompt":"smooth-turn-compression-v1"` → `"prompt":"detailed-turn-compression-v1"`). Uses `REPLACE(metadata, old_json, new_json) WHERE metadata LIKE '%old_json%'`.
5. **`derivation_log.payload` JSON**: Same REPLACE for provenance inside payload JSON.
6. **`log.message` text**: The derivation type appears in human-readable log messages.
7. **`thread_view` JSON columns**: The arrangement, gaps, and source-state JSON all store derivation type strings. Three REPLACE calls on three columns in one UPDATE.

This is a rare case of needing to search-and-replace inside JSON stored in SQLite. The approach is safe because the old/new strings are known constants, not arbitrary user data, and the REPLACE only fires on rows that LIKE-match. But it's fragile: if any new table or column stores the derivation type string, it would need to be added here.

### The Queued Work Item Migration (`migrateQueuedTurnDerivationWorkItems`)

This is the most subtle migration. It runs **on every open**, not just during version upgrade. The reason: the architecture changed how `turn_derivation` work items target their derivations.

**Before**: A `turn_derivation` work item's payload.derivations listed `[turn_rendering, smooth_turn_compression]`. The handler composed both and completed them in one pass.

**After**: The handler produces `[turn_rendering, pre_detailed_assembly]`. Compression is a separate `detailed_turn_compression` work item enqueued from the turn_derivation handler's `onApplied` hook.

So any in-flight `turn_derivation` items from before the change have the wrong derivation targets. The migration:

1. Find all `turn_derivation` items with status `queued` or `claimed`.
2. For each, parse the payload and check if it has the legacy shape (has `turn_rendering` and a compression type but no `pre_detailed_assembly`).
3. If so: rewrite the payload's derivations to `[turn_rendering, pre_detailed_assembly]`.
4. Also seed a `pre_detailed_assembly` derivation row (`INSERT OR IGNORE`) at the item's source version, so the completion's UPDATE has a row to hit.

The `INSERT OR IGNORE` is important: if the migration runs twice (idempotent), the seed is a no-op. The `turnDerivationPayloadNeedsPreDetailedAssembly` check is precise: it only triggers when `turn_rendering` is present AND a compression type is present AND `pre_detailed_assembly` is absent. An already-migrated item (which has `pre_detailed_assembly`) passes through unchanged.

There's also a secondary path: if the payload already lists `pre_detailed_assembly` but no derivation row exists for it yet, the migration seeds the row. This handles the edge case where the payload was migrated but the process crashed before the derivation row was created.

### Why It Runs on Every Open

The comment says "idempotent — safe on every open." This is necessary because:
1. A process crash could leave a half-migrated item (payload rewritten but derivation row not seeded).
2. A `turn_derivation` item could be claimed by a handler that was loaded before the migration ran — the old handler would produce the wrong writes, failing the `assertExactDerivationWrites` check. Running the migration on every open ensures the items are in the expected shape before any handler touches them.

The idempotency guarantee comes from:
- `INSERT OR IGNORE` for the derivation row seed
- The payload check (`turnDerivationPayloadNeedsPreDetailedAssembly`) returning false for already-migrated items
- The whole thing running in `BEGIN IMMEDIATE` so it's atomic

## The Fail-Closed Guard Design

### The Three Layers

**Layer 1 — The `guard` wrapper** (every Epic 1 hook):

```typescript
const guard = (name, body) => async (event, ctx) => {
  try { await body(event, ctx); }
  catch (err) {
    lastDiagnostic = { code: "hook_handler_error", message: `${name}: ${err.message}`, recordedGap: false };
  }
};
```

Every hook body is wrapped. The catch produces a plain-data diagnostic and **never rethrows**. A thrown hook in PI breaks the user's session — this ensures that can never happen from pi-lhc. The diagnostic says `recordedGap: false` because if we threw before capture, no gap was written.

**Layer 2 — The `capture()` function** (converter.ts):

```typescript
async function flushIsolated(instance, events) {
  try { return await instance.sdk.intakeStream.messageEvents(instance.threadRef, events); }
  catch (cause) {
    return { ok: false, error: { errorClass: "system_error", code: "storage_failure", reason: `capture flush threw: ${detail(cause)}` } };
  }
}
```

Even though `messageEvents` returns `OpResult` by contract, the thread file could be in a genuinely broken state where the call throws (SQLite internal error, file deleted mid-operation). `flushIsolated` catches that too and returns a structured result. **No throw escapes.**

When `capture` gets an `invalid_event` error (validation failure on a writable thread), it records a durable gap:

```typescript
if (primary.error.code === "invalid_event") {
  const gap = await flushIsolated(instance, [gapNote(events, primary.error.reason)]);
  if (!gap.ok) return gap;  // gap write itself failed → store unavailable
  return primary;            // original failure with recordedGap trackable
}
```

The gap note is a `runtime_note` event with a fingerprinted idempotency key (`pi-lhc:gap:<sha256(events+reason)>`). This makes the gap:
- **Durable**: It's in the event table, readable by `listEvents` and surfaced in `inspect.health`.
- **Deduplicated**: Re-delivery of the same bad batch produces the same gap key → skipped.
- **Queryable**: `inspect.health` scans events for `captureGap` text patterns.

**Layer 3 — The `recordCaptureOutcome` function** (index.ts):

```typescript
function recordCaptureOutcome(result, events) {
  if (result.ok) { delete state.health.lastCaptureFailure; return; }
  const recordedGap = result.error.code === "invalid_event";
  const failure = { code: result.error.code, message: result.error.reason, recordedGap };
  lastDiagnostic = failure;
  if (state !== null) state.health.lastCaptureFailure = failure;
}
```

Every capture result is classified:
- **Success**: Clear the health failure flag. Clean slate.
- **`invalid_event`**: The gap was recorded durably (layer 2 did it). Mark `recordedGap: true` in the health diagnostic.
- **Anything else** (store unavailable): No durable gap possible. Mark `recordedGap: false`. The failure is only in-memory in `state.health.lastCaptureFailure`.

### Fork Detection Fail-Closed Design

Fork detection has two tiers:

**Tier 1 — Hook-based** (`session_before_fork`): PI fires this before a fork. The handler captures `pendingFork = { sourceThreadRef, forkEntryId }`. On the next `session_start`, this pending fork drives the create-and-seed path.

**Tier 2 — Session-tree fallback** (`detectForkFromSessionTree`): If `session_before_fork` didn't fire (older PI, race, etc.) but `event.previousSessionFile` is present and `state` holds a prior thread ref, the connector reads the previous session's JSONL file, builds a set of its entry ids, then:
1. Finds the latest current entry whose id is also in the previous session (shared ancestry point).
2. Or finds the first current entry with a `parentId` pointing into the previous session.

Either way, the fork point is inferred and the same create-and-seed flow runs.

Fork seeding itself is fail-closed: `seedFork` reads all events from the source, filters to the fork point by parsing idempotency keys for the fork entry id, includes the trailing `turn_end`, and replays through normal `intakeStream.messageEvents`. If any step fails, the fork is aborted, the instance is disposed, and state is cleared. No half-seeded thread is left operational.

### The Launcher Hydration Fail-Closed Design

`prepareLhcLauncherStartup`:
1. Resolve thread → fail with error if null
2. `initInstance` (validates the thread file) → fail with error if invalid
3. Create `SessionManager.inMemory`
4. `seedPiSessionFromLhc` → reads `getSessionThreadView` → fail with error if thread view fails
5. Append `pi-lhc.thread` entry
6. **Always `disposeInstance`** in `finally` — the temporary read instance is closed whether seeding succeeded or failed

The `setLauncherOwnedStartup` handoff is one-shot: `takeLauncherOwnedStartup` clears the slot on consumption. If `session_start` runs without consuming it (impossible in normal flow but guarded against), the slot is empty on the next start and normal resolution runs.

# Long Horizon Context: Core Concepts

Long Horizon Context (LHC) is an SDK for managing an agentic harness's context and history. It keeps the full message history of a conversation as a durable record, and from that record builds shorter, summarized views that a harness can load and work from.

## Basics

LHC is a stateful SDK consumed in-process by a host. The host — a PI extension today; a web or desktop app server later — creates an SDK instance at startup via `initLhc`, wiring in everything LHC needs: storage location, configuration, and a way to make model calls. There are two ways to give LHC model access: hand it a complete set of inference callback functions directly, or hand it one model-calling function plus a table of which provider/model to use for each kind of derivation work (the adapter resolves this into callbacks internally). LHC has no logins of its own and no out-of-process surface; anything that needs to talk to LHC runs inside a host that holds an SDK instance.

All durable state lives in storage — one SQLite file per thread, plus a separate SQLite registry that tracks which threads exist and where their files are — so a host can stop and restart without losing anything, including queued background work, which picks up where it left off.

The system is organized into domains, each owning one part of the conversation model and exposing its operations through the SDK surface. Beneath them sit shared-tech utils — a durable work queue, a token counter, an inference adapter, a prompt registry, and a scheduler — that the domains use but that have no surface of their own. One cross-cutting technical surface — logging — is exposed externally as well: both LHC and the host write info/warning/error logs through it, stored in the thread's SQLite file.

## Key domains and entities

**Threads.** A thread is the durable container for one ongoing conversation between a user and an agentic harness, and each thread lives in its own file. The `threads` domain creates threads, keeps the registry of which threads exist and where their files are, and holds thread-level metadata and status. Thread ids are globally unique (`th_` + 16 hex chars) and support partial-prefix resolution.

**Intake stream.** As a harness runs, it produces a stream of events: user prompts, assistant text and thinking, tool calls and their results, model changes, thinking level changes, runtime notes, and a marker at the end of each turn. The `intake-stream` domain takes these events in ordered batches and records them into the thread. As it records the stream, it calls `messages` to create the readable message-and-block view and calls `turns` to apply the turn state machine.

**Messages.** A message is one unit of the conversation — a user prompt, assistant text, assistant thinking, a tool call, a tool result, a model change, a thinking level change, or a runtime note — built from typed blocks. The five block types are `text`, `tool_call`, `tool_result`, `model_change`, and `thinking_level_change`. The `messages` domain owns this message-and-block view. It creates messages when called by intake-stream, lets you list and show them, and gives people or agents a place to edit or remove messages from the readable record.

**Turns.** A turn is one full exchange: a user prompt and all the assistant and tool activity that follows it, up to a `turn_end` or the next prompt. The `turns` domain owns turn state, derives closed turns, and groups turns into chunks that feed summaries and recall. Turns are the base unit; chunks are containers of turns. There is always exactly one open turn at any time — this invariant is enforced as a hard error.

**Thread views.** A thread view is a summarized, harness-ready rendering of a thread, produced by a smart compact and arranged so an agent can resume the conversation without the full history. A view is a snapshot: it changes only when the next compact replaces it, never on its own. What a harness loads is the stored view plus the live tail — everything recorded since the compact. The `thread-view` domain produces views, serves them as model context, and writes them into a host-specific file format (today PI session JSONL).

**Inspect.** The `inspect` domain looks at a thread as a whole, producing overviews, health reports, and view-contents reports across its messages, turns, and views. It reads through other domains' surfaces and changes nothing. Where `messages` works inside the history, `inspect` reports on the state of it.

## What we call things

The working vocabulary of the project. Each entry says what the term means and, where it matters, where its edge is — the nearby thing it should *not* be confused with.

**Record.** The durable, append-only source of truth: the events as they arrived. Everything else is built from the record and can be rebuilt from it. Edits and deletes change what readers see; the record retains the originals.

**Derivation.** The stored output of producing a new representation of existing content — a smoothed prompt, a tool-result summary, a chunk summary — attached to its source. To **derive** (deriving) is the act; a **derivation** is the stored result. **Derivation type** names which one. Deriving runs either in the background off the work queue or synchronously through explicit derive operations on the domain surfaces — never on the intake hot path.

**Derivation types.** The system has six derivation types, each owned by one domain. Four are produced by calling a model; two are assembled deterministically from other material:

- `smoothed_prompt` — cleans up a user prompt; inference-backed (owned by messages)
- `tool_result_summary` — summarizes a tool result; inference-backed (owned by messages)
- `turn_rendering` — composes a turn's activity into one account from its message-level derivations; deterministic (owned by turns)
- `smooth_turn_compression` — compresses a turn rendering for the smooth band; inference-backed (owned by turns)
- `chunk_summary_detailed` — assembles a chunk summary from member turn compressions and tool-activity receipts; deterministic (owned by turns)
- `chunk_summary_brief` — summarizes a chunk, keeping outcomes only; inference-backed (owned by turns)

**Derivation states.** Every derivation carries one of four states: `pending` (expected or in flight), `ready` (usable), `failed` (terminal, with a reason), `blocked` (source damage; retry won't help). Retry-in-progress is not a state — a derivation stays `pending` while attempts remain. Mechanical retry detail (attempt counts, backoff) lives on the queue row, not the derivation. State belongs to the derivation itself, never to its subject — a chunk does not have "a state"; its detailed derivation and its brief derivation each carry their own.

**Source version.** A monotonic version on each derivation row, incremented when the source content changes — through an edit, a delete, or a cascade from a changed dependency. When a derivation is in flight and the source changes, the rebuild writes at the next version. The in-flight derivation finishes against the old version and is discarded as stale. This prevents a late-finishing pre-change derivation from overwriting a post-change rebuild.

**Work queue / drain.** The durable per-thread queue of background work. Rows are written in the same transaction as the change that caused them, so queued work survives crashes. **Draining** is processing that queue — claim an item, run the handler, write the result — until the queue is empty or stopped. Handlers may call inference or assemble deterministically depending on the derivation type. Draining happens inside the host's process; there is no daemon.

**Host mode.** LHC runs in one of two modes, chosen at SDK construction:

- **Background**: derivation work runs automatically. After each intake commit, the scheduler picks up queued items and drains them. When a thread file is opened for the first time in a process, leftover work from a previous process is drained too.
- **Manual**: derivation work runs only when the host explicitly calls `work.drain`. The scheduler is inert.

**Smoothing.** The derivation that cleans up a user prompt — typos, repetition, heat — while preserving intent, constraints, and exact identifiers. The smoothed derivation is what views render; the original stays in the record.

**Turn.** One full exchange: a user prompt and everything that follows it, up to the turn's end. **Chunk:** a container of consecutive closed turns, cut by a token-based size policy, whose membership never changes once closed.

**Bands.** The fidelity tiers a thread view is built from, oldest to newest: **brief** (shortest chunk summaries), **detailed** (fuller chunk summaries), **smooth** (compressed turn renderings). These three are rendered and stored as snapshot text by a compact. The **full** tier is not stored — compact uses its percentage to determine where the compact point falls, and everything after that point is served as the live tail. A compact decides how much of the thread lands in each tier.

**Smart compact.** The explicit operation that produces a new thread view. It takes a compact configuration — a target size in tokens and a set of percentages that control how much of that size each band gets — and arranges the thread's turns and chunks into bands accordingly. Compact never calls a model; it assembles from derivations that already exist. Missing derivation material degrades the entry (falls back to a cruder derivation, a deterministic floor, or raw content). Damage to the canonical record itself — such as a turn referencing a missing chunk member — causes compact to refuse before writing, leaving the prior view intact.

The SDK ships built-in compact configurations that can be overridden or extended at construction, and callers can override individual percentages at compact time.

**Compact point.** Where the most recent compact stopped. Everything after it is the **tail** (or live tail): recent activity served alongside the view. Before an explicit smart compact, tail tool results render full. After compact, a visibility boundary may shorten at-or-behind tool results.

**Visibility boundary.** A per-thread marker that controls how tool results appear in the model context: tool results at or behind it render as a deterministic truncation with a pointer back to the full record, tool results ahead of it render full. Intake does not advance it automatically — pre-compact resume and session-view keep full tool results. Compact resets the boundary to the compact point. It affects only tool results — prompts, assistant text, and thinking always render full.

**Inference callbacks.** The four-operation interface that sits at the boundary between LHC and the host's model access: `smoothPrompt`, `summarizeToolResult`, `compressSmoothTurn`, and `summarizeChunkBrief`. Any model call LHC makes goes through this interface. Deterministic derivations such as `turn_rendering` and `chunk_summary_detailed` stay inside their owning domain handlers and do not cross the inference boundary.

**OpResult.** The error contract. Every operation that can fail returns either `{ ok: true, value }` or `{ ok: false, error }`. The error carries a machine-readable `code`, a human-readable `reason`, and an `errorClass` (`caller_error`, `state_corruption`, or `system_error`). Expected failures are always returned this way, never thrown. Programmer bugs inside LHC may still throw, but callers are not expected to handle throws as contract outcomes.

**Logging surface.** A cross-cutting technical surface, exposed externally from LHC, that both LHC and the host call to write info/warning/error logs into the thread's SQLite file. Writes are fail-soft — a logging failure never propagates to the caller and never shares the caller's transaction. It carries diagnostics (such as a derivation falling back to a floor) collected for troubleshooting, not control flow. Distinct from the record: logs say what went wrong, the record stays what is usable.

**Degraded / gap.** What a view shows when a needed derivation is missing: a **degraded** entry renders the best available fallback (a cruder derivation, a deterministic floor, or raw content); a **gap** is an explicit placeholder where nothing usable exists. The fallback goes into the view (more content, not less) and the failure goes to the log; the record stays clean. Nothing is silently omitted.

**Render / materialize / LlmRequestContext.** Three ways view content leaves LHC: **render** is producing the output form of an entry; **materialize** is writing the view to a file in a host-specific format (today PI session JSONL); **LlmRequestContext** is the host-facing model context returned by `threadView.getLlmRequestContext`. Both materialized and in-memory forms come from the same serving assembly; only the output shape differs.

**Host.** The process that owns an SDK instance and everything LHC needs from the outside world: storage location, configuration, model access. PI extension now; app server later; possibly a wrapper around another harness someday. One login — the host's — covers everything LHC does.
# Long Horizon Context: Domain Design

This document describes each domain in more depth: what it stores, the operations it provides, and the other domains it calls. It builds on the vocabulary in 01-core-concepts.md.

## Domain surfaces

A domain is both a vocabulary area and a service surface. The operations a domain exposes are the same operations everywhere they are reached: the host calls them as SDK functions in-process, a future app server can serve them as endpoints, and other domains call them in-process when they need work the domain owns. When one domain needs something from another, it calls that domain's surface; it does not reach into the other domain's storage or internal modules. (Thread-view still has direct reads against message and turn tables for live-tail assembly and visibility-boundary decisions; these are known cleanup debt, not a design choice.) One domain can coordinate a flow that spans several, the way `intake-stream` records a batch and calls `messages` and `turns` along the way, but the called domains keep ownership of their own work.

## Shared-tech utils

Beneath the domains sit a small number of **shared-tech utils**: shared machinery that domains use but that owns no part of the conversation model. A tech util is not a domain. It has no domain surface and no vocabulary of its own in the product; it is internal plumbing (the logging surface is the one util exposed externally, but it owns no part of the conversation model). The dependency runs one way: domains use tech utils, and a util never calls a domain or contains domain logic. Shared-tech can carry domain-shaped identifiers and work-kind names as mechanism data, but the meaning of a turn, a chunk, or a summary stays the owning domain's business.

The **durable work queue** records background work as durable items in the thread's SQLite file. An item commits in the same transaction as the change that caused it, so queued work survives crashes. Items are processed one at a time per thread: the drain loop claims an item under BEGIN IMMEDIATE, runs the owning domain's handler with no open transaction, and completes in a second short transaction that writes the derivation and deletes the item. The handler may call inference or assemble deterministically depending on the derivation type. Claims are fenced by a monotonic epoch so a stale completion can never stamp a derivation that has moved on. Two properties carry the design: pending work is recorded durably, not held in memory, so a restart loses nothing; and a thread's queued work is ordered, so work queued by an edit lands after work already in flight on the old content. Failed handlers are retried up to a configured budget with exponential backoff; a handler that exhausts retries or fails non-retryably lands its derivation as `failed` with the final reason, and the work item is deleted.

Each kind of queued work has exactly one owning domain. A domain queues its own work; it never queues work into another domain, and no domain watches for another domain's items. When a flow crosses domains, the crossing is a surface call, and the called domain queues whatever work its part needs. The queue owns the mechanics of an item: recorded, claimed, retried, finished. What the work means belongs entirely to the owning domain.

Derivations carry state. The four states are one shared vocabulary across domains: `pending`, `ready`, `failed`, `blocked`. What a state means for a particular derivation stays the owning domain's call. State belongs to the derivation itself, never to its subject. Whether a failed attempt will be retried is the work queue's business, not a property the derivation duplicates; a domain's derivation report joins the two, so a caller asking "is this still coming?" gets the answer without reading queue mechanics.

The **inference adapter** bridges the host's model access into LHC's derivation handlers. Each derivation type that needs inference has a model assignment (provider, model, prompt template name). The adapter renders the prompt from the registry, calls the host's function, classifies failures as retryable or terminal, and returns shaped text with config-known provenance. Large inputs are bounded before rendering. Empty model output is rejected. Host exceptions and timeouts are contained. Derivation types whose handlers assemble deterministically never reach the adapter.

The **prompt registry** is the name-keyed set of prompt templates. Model assignments select templates by name; versioning is in the name (e.g. `smoothing-v1`, `tool-result-v1`). Adding or replacing a template for an existing derivation type is a module addition; no handler or adapter changes are needed. A new derivation type would require handler, config, and adapter work.

The **scheduler** manages per-thread drain scheduling in background mode. Post-commit pokes trigger drains; first-touch catch-up drains process leftover work from previous process lifetimes. Per-thread single-flight with pending-flag coalescing: at most one drain runs per thread, with at most one pending pass queued behind it. Wake timers handle retry backoff eligibility and claim expiry. In manual mode the scheduler is inert — the host must call `work.drain` explicitly to process queued work.

The **instance seam** isolates multiple SDK instances in the same process. Every SDK operation runs inside its instance's async-context scope, so enqueue pokes and thread-file touches reach that instance's scheduler, not another's. A manual SDK's operations deliver to a no-op seam, so a background SDK in the same process can never auto-drain the manual SDK's work.

Local **token counting** stamps estimates on messages when they are created and on derivations when they land, using a shared local tokenizer (`o200k_base` encoding). The count is stored once and is stable and reproducible: the same text always yields the same number.

**Logging** is a cross-cutting technical surface that, unlike the other utils, is exposed externally from LHC. Both LHC and the host write info/warning/error logs through it, stored in the thread's SQLite file. Writes are fail-soft — a failure never propagates and never shares the caller's transaction. The record stays what is usable; the log says what went wrong.

## Threads

A thread is the durable container for one ongoing conversation. The `threads` domain creates threads, tracks where they live, and gives the rest of the system a way to find a thread by id. Two SQLite databases sit behind it:

- A listing of all threads is stored in a **thread registry** database, with one row per thread holding its id, file path, optional title, optional cwd, and creation timestamp.
- Each thread's own database holds that thread's full record: its events, messages, turns, chunks, and views. Reading or changing a thread's contents means opening its file.

The thread file is authoritative for its own identity. It stores its thread id once, as identity metadata. The records inside it (events, messages, turns) do not each carry the thread id, because the file is the thread. The thread registry is a convenience lookup over the thread files, not the authority.

### Creating a thread

`newThread` creates a thread at a given file path, sets up the empty thread inside it (including seeding one open turn), and adds a row to the thread registry. It generates a thread id and records the id-to-path mapping. If a file already exists at the path, the operation fails instead of touching it. Creation spans two databases that cannot share a transaction; the order is file-then-row so the invariant "no registry row without its file" is absolute. An orphan file from a crash between the writes is harmless.

```mermaid
sequenceDiagram
  participant C as user or harness
  participant T as threads
  participant F as thread file
  participant R as thread registry
  C->>T: newThread (file path)
  T->>F: create thread file (schema + metadata + open turn)
  T->>R: add row (id, file path)
  T-->>C: thread id
```

### Finding a thread by id

A thread id is the primary, stable key a caller holds. It survives the thread file moving, which a file path does not. Other domains work with thread references (`ThreadRef`), which can be `{ threadId }` or `{ filePath }`. When a domain needs to act on a thread, it asks the threads domain to resolve the reference to a file path, then opens it. Resolution from a thread id accepts a full or partial (prefix) id: an exact match wins outright; a unique prefix resolves; an ambiguous prefix fails naming the collision.

```mermaid
sequenceDiagram
  participant D as a domain with a ThreadRef
  participant T as threads
  participant R as thread registry
  participant F as thread file
  D->>T: resolve ThreadRef to file path
  T->>R: look up id (exact or prefix)
  R-->>T: file path
  T-->>D: file path
  D->>F: open and act on the thread
```

### Browsing threads

A user who wants to see their threads starts at the threads domain. `listThreads` lists threads from the registry, optionally filtered by cwd. `resolve` looks up a thread by id. `info` reads the thread file's own identity metadata (thread id and creation timestamp). From a list, a user picks a thread and drills into its messages, turns, or views through the other domains.

```mermaid
sequenceDiagram
  participant C as host UI
  participant T as threads
  participant R as thread registry
  participant F as thread file
  participant O as messages, turns, thread-view
  C->>T: listThreads, resolve
  T->>R: read listings
  R-->>T: rows
  T-->>C: threads
  C->>T: info
  T->>F: read thread_metadata
  F-->>T: identity
  T-->>C: thread info
  C->>O: drill into one thread
```

## Intake stream

As a harness runs it produces a stream of events. An event is one recorded thing that happened in the thread:

- `user_prompt`: a prompt from the user, or an automated prompt that stands in for one
- `assistant_text`: assistant output text
- `assistant_thinking`: assistant reasoning
- `tool_call`: a tool invocation
- `tool_result`: the result of a tool invocation
- `model_change`: a switch from one model to another
- `thinking_level_change`: a change in the thinking level
- `runtime_note`: a note from the harness or runtime
- `turn_end`: a marker that the current turn is complete

The `intake-stream` domain takes these events in and writes them into the thread in the order they happened. It is the only way thread content enters the system from a harness.

These flows are about how data moves, not about a user interface. The operations exist to record incoming events and coordinate the synchronous domain work that follows from those events. As it records the stream, `intake-stream` calls `messages` to create the readable message-and-block view and calls `turns` to apply the turn state machine. Those calls are in-process calls to the domain surfaces, not separate service hops.

A thread is single-threaded by definition: one conversation, one stream. The design model is one ordered time series per thread, which lets boundary decisions be made from position in that stream.

### The stream contract

The harness owns sending a coherent stream. The domain does not reconstruct order or membership from a malformed stream; it records what it is given, in the order given, and fails loudly when the stream implies an impossible state.

The contract:

- send events in the order they happened
- send a `turn_end` when a turn is complete
- there is always exactly one open turn at any time

### Taking in events

A harness sends a batch of one or more events for a thread. The thread reference rides outside the batch, since every event in a batch belongs to the same thread. The host calls the SDK operation with typed event objects directly (`intakeStream.messageEvents(threadRef, events)`).

The domain resolves the thread reference to its file through the threads domain, then writes the batch to the thread's database in one coherent write flow. For each event it assigns the next position in the thread's order and records the source event. For events that produce readable conversation activity, it calls the `messages` surface to create messages and blocks. For events that affect turn state, it calls the `turns` surface to apply the turn state machine. It returns a result describing what happened to each event.

```mermaid
sequenceDiagram
  participant H as harness
  participant I as intake-stream
  participant T as threads
  participant M as messages
  participant U as turns
  participant F as thread file
  H->>I: messageEvents (ThreadRef, events)
  I->>T: resolve ref to file path
  T-->>I: file path
  I->>F: record source events
  I->>U: apply turn state machine
  I->>M: create messages and blocks
  I-->>H: per-event result
```

Events carry an idempotency key from the harness. If an event with the same key was already recorded for the thread, it is skipped rather than written twice, so a harness that resends a batch after a failure does not produce duplicates.

### Turn boundaries are decided here, synchronously

Turn boundaries are decided in the hot path, as events land, while intake is the thing watching the ordered stream. `intake-stream` calls the `turns` surface to apply the turn state machine and get the turn membership for message-producing events. This keeps membership correct: a message is attached to its turn when it is recorded, not inferred later against a stream that has moved on.

The deterministic work is synchronous: recording events, calling `messages` to create messages and blocks, calling `turns` to apply the state machine, attaching messages to the current turn, and assigning token estimates. Smoothed prompts and tool-result summaries are queued as durable work when each message lands; turn compression and chunk summaries are queued when the turn or chunk closes. Closing a turn settles its membership immediately; the derivation work that follows operates on a turn whose contents are already frozen.

There is always exactly one open turn. Thread creation seeds the first open turn. A `turn_end` with members closes the current turn, queues its derivation work, and immediately opens a new empty turn. A `user_prompt` arriving when the current open turn already has members does the same: closes the current turn, opens a new one, and the prompt becomes the new turn's first member. A `turn_end` with no members is a no-op — the empty open turn stays open. A `user_prompt` arriving into an empty open turn simply becomes its first member; no close happens.

| Event | Current open turn | Action |
| --- | --- | --- |
| `user_prompt` | has no members | prompt becomes first member of current turn |
| `user_prompt` | has members | close current turn (+ queue work), open new turn, prompt is first member |
| `turn_end` | has members | close current turn (+ queue work), open new empty turn |
| `turn_end` | has no members | no-op |
| any other event | — | add to current turn |

More than one open turn is a hard error during this phase — an invalid thread is caught and triaged instead of producing quietly wrong turns later.

### What the result reports

The result reports, per event, whether it was recorded or skipped as a duplicate. An invalid batch returns an `OpResult` error and rolls back the entire transaction, so a batch either lands cleanly or not at all. The result also reports turn transitions that the batch opened or closed, and queued work items.

## Messages

A message is the readable form of activity in a thread. The `messages` domain owns the message-and-block view of the conversation. It creates that view from source events, lets callers read it, and provides the place where later message-level edits and deletes happen.

Events and messages are different records. Events are the ordered source stream received from a harness. Messages are the normalized view created from those events so the rest of the system can read, list, edit, group, and assemble thread history. A `turn_end` changes turn state but does not produce a message.

### Creating messages

`intake-stream` calls the `messages` surface as it records incoming events. The message operation creates a message for events that should appear in the readable conversation and creates the blocks that belong to that message. It also stores the token estimate for the message's original content. Message ids are deterministic: `m` followed by the event's order number.

```mermaid
sequenceDiagram
  participant I as intake-stream
  participant M as messages
  participant F as thread file
  I->>M: create message from recorded event
  M->>F: write message and blocks
  M-->>I: message id and token estimate
```

### Messages and blocks

A message represents one meaningful piece of conversation activity: a user prompt, assistant text, assistant thinking, a tool call, a tool result, a model change, a thinking level change, or a runtime note. Each message contains one or more typed blocks. The five block types are `text`, `tool_call`, `tool_result`, `model_change`, and `thinking_level_change`. Most message kinds — user prompts, assistant text, assistant thinking, runtime notes — project to a `text` block. Tool calls, tool results, model changes, and thinking level changes each project to their own block type.

### Message-level derivations

Some derivations belong to a single message and need nothing beyond it, so `messages` owns them and queues their work the moment the message lands, without waiting for a turn to close.

A user prompt gets a `smoothed_prompt` derivation: cleaned and attenuated with its content preserved, queued when the prompt lands. If the cleaned text exceeds a configured token threshold, the cleaned text itself becomes the derivation without calling inference.

A tool result gets a `tool_result_summary` derivation. The full output is stored when its message is created and is never discarded. The summary is produced by inference, carrying derivation state and able to fail. Large tool results (above the `largeTierTokens` threshold) get an immediate deterministic truncation instead of queuing inference work. Every tool-result summary states its outcome mechanically — succeeded, failed, or unknown — stamped from the record, never authored by model text.

Tool calls are kept as-is, not summarized: call arguments are usually short, so no separate derivation pass is needed.

### Token estimates

Each message is stamped with a token estimate of its original content when it is created, in the same synchronous step that writes the message. Stamping on creation means every message carries a size the moment it lands, with no later counting pass, and a turn's size is the sum of its messages' estimates as soon as the turn closes.

The estimate comes from a local tokenizer (`o200k_base` encoding). The same text always yields the same number, with no provider call and no failure mode.

### Reading messages

The messages domain lists and shows messages for a thread. It is the lowest-level human-readable view of the conversation.

- `list` returns messages in record order, with optional bounds (from/to event order), limit, and an opt-in to include deleted records.
- `show` returns a single message with its complete blocks, full content, and its derivation report entries with queue-joined state.

```mermaid
sequenceDiagram
  participant C as host UI or agent
  participant M as messages
  participant T as threads
  participant F as thread file
  C->>M: list or show
  M->>T: resolve ref to file path
  T-->>M: file path
  M->>F: read messages and blocks
  F-->>M: message records
  M-->>C: messages
```

### Editing and deleting messages

Manual cleanup goes through messages, not `intake-stream`. Intake-stream records new activity from a harness; messages is where a person or agent can later correct or prune the readable conversation record. Two operations do this: `edit` changes a message's content, and `remove` removes a message from the readable record. Both target closed turns only; the open turn is the live exchange and stays out of reach.

`remove` is a soft delete: the message drops from reads and from its turn's membership, but the source events it was created from stay in the event log; the record underneath is never destroyed. Removing a message that initiates a turn (the prompt) is refused; the `remove` surface handles individual non-initiating messages only.

An edit runs the same way creation does. The deterministic work happens synchronously: the message and its blocks are updated and the token estimate is re-stamped. Derivations built from the old content are cleared and their work is queued again by the domains that own them, each at the next source version so a late-finishing pre-edit derivation is discarded as stale. An edit never leaves an old derivation in place to be judged against new content later.

A remove cascades the same way, with one difference: the removed message's own derivations drop rather than re-queue — their source is gone — while everything composed above it rebuilds. The cascade is bounded by structure: a message affects its turn's composed rendering, and that turn's containing chunk re-derives its detailed and brief summaries. Neighboring chunks never re-derive, and chunk boundaries never move; a chunk shrinks in place, never re-cut.

### Synchronous derivation

In addition to the background queue path, the messages surface exposes `derive` — a synchronous operation that runs derivation work inline for a list of message ids. It claims a work item, runs the handler, and writes the result, or returns immediately if equivalent work is already in flight. This is available for callers that need a derivation now rather than waiting for the background drain.

## Turns

A turn is one exchange in a thread. In the normal harness stream it starts with a `user_prompt`, or an automated prompt that stands in for one, and includes the assistant text, assistant thinking, tool calls, tool results, model changes, thinking level changes, and runtime notes that follow. A turn closes when a `turn_end` arrives with members, or when the next `user_prompt` arrives and the current turn has members.

The `turns` domain owns turn state, turn records, and turn-based containers such as chunks. It exposes the operations that apply the turn state machine during intake, and it derives closed turns into the representations that later feed bands and thread views.

### The turn state machine

`intake-stream` calls the `turns` surface as it processes incoming events. The turn state machine maintains the invariant that exactly one open turn exists at all times. The result tells intake which turn a message-producing event belongs to.

```mermaid
sequenceDiagram
  participant I as intake-stream
  participant U as turns
  participant M as messages
  I->>U: apply turn state for event
  U-->>I: current turn membership
  I->>M: create message with turn membership
```

### Deriving closed turns

Closing a turn makes its membership stable. The work that follows runs after the close and is queued durably in the same transaction:

- **`turn_rendering`** — a deterministic composition of the turn's activity from its message-level derivations. Smoothed prompts and tool-result summaries are used where ready; deterministic floors fill in where they are not. Tool calls and results that form a consecutive stretch are composed into a single run-level account that names the tools, counts the calls, and tallies the mechanical outcomes. The rendering carries tool-run receipts — structured records of what each run did and how it ended — so that chunk summaries can read outcomes without re-deriving anything.

- **`smooth_turn_compression`** — an inference-backed compression of the turn rendering for the smooth band. This is the slow work; the rendering composition above is deterministic and fast.

Both derivations are queued together as one work item. When the handler runs, it composes the rendering first, then sends the rendering through inference for compression. Both derivation results are written in one completion transaction.

The `turns` surface exposes operations to check derivation state, re-queue failed work, and run derivation synchronously (`deriveTurn`).

### Chunks

A chunk is a container of turns. Chunks let the system group multiple closed turns into larger units that can be summarized and placed into lower-fidelity bands. Turns are the base unit; chunks are the next container above them.

The `turns` domain owns chunk formation because chunking depends on turn order, turn size, and the token cost of smooth turn compressions. Closed turns accumulate into the current open chunk. The chunk close policy is a deterministic arithmetic check against configured thresholds (`targetProjectedTokens` / `maxProjectedTokens`) over stored projected token counts — identical streams produce identical chunk boundaries across restarts. Chunk placement — assigning a turn to a chunk — happens inside the turn derivation handler's completion transaction, so a crash leaves either a placed turn with its enqueued summaries or nothing, never a derived-but-unplaced turn.

A closed chunk gets two derivations, queued in the completion transaction:

- **`chunk_summary_detailed`** — a deterministic assembly from member turn compressions and their tool-run receipts. Keeps the texture of what happened: what was changed and whether it succeeded.

- **`chunk_summary_brief`** — an inference-backed summary that keeps outcomes only. What ages out first is the activity's texture, never its result.

Both carry derivation state and can be checked through the `turns` surface. Chunk summaries wait on their member turn compressions: if a member's `smooth_turn_compression` is not ready, the chunk summary handler requeues; if it is blocked, the chunk summary lands blocked.

### Reading turns and chunks

The turns domain lists turns and chunks for a thread. These operations are used by agents and users who want to inspect the conversation at a higher level than individual messages, and by thread-view when it needs turn and chunk material for context assembly. Each record carries its derivation states alongside it.

```mermaid
sequenceDiagram
  participant C as host UI or agent
  participant U as turns
  participant T as threads
  participant F as thread file
  C->>U: list turns or chunks
  U->>T: resolve ref to file path
  T-->>U: file path
  U->>F: read turns and chunks
  F-->>U: turn and chunk records with derivation states
  U-->>C: turns and chunks
```

## Thread view

A thread view is a summarized, harness-ready rendering of a thread. It holds enough of the conversation for an agent to resume work without the full history: recent activity at high fidelity, older activity compressed into shorter representations. The `thread-view` domain stores compact snapshots and serves them with the live tail. Its operations are `getLlmRequestContext`, `status`, `describe`, `compact`, and `materialize`. A harness either loads a view that LHC has written to a file or asks LHC for the current `LlmRequestContext` directly.

A view is a rendering, not a second copy of the conversation. It is assembled from records the other domains already own: messages, turns, chunks, and the derivations derived from them. Producing a view never changes the canonical history; it selects and arranges what already exists.

### Bands

A thread view is arranged in bands of decreasing fidelity, from the most recent activity down to the oldest:

- **full**: recent turns and messages served live from the record (the tail)
- **smooth**: compressed turn renderings
- **detailed**: detailed chunk summaries
- **brief**: brief chunk summaries — the compressed floor of the view

The bands are a gradient, not a cliff. As a turn ages it moves down a band, losing fidelity in steps instead of dropping out of the view all at once. The recent end stays sharp for the work in progress; the old end stays cheap while still carrying the shape of what came before.

Of the four tiers, three — brief, detailed, and smooth — are rendered and stored as snapshot text by a compact. The full tier is not stored; compact uses its percentage to determine where the compact point falls, and everything after that point is served live.

### Generating a view

Generating a view — the operation a user or host invokes as a **smart compact** — sets the band arrangement for the whole thread: which turns and chunks fall into which band, rendered into a current view. It takes a compact configuration (a target size in tokens and percentages per band) and works by selecting artifacts the other domains have already derived, not by recomputing them. Compact never calls a model; it is assembly, not summarization.

Compact is an explicit operation, invoked by the host or caller. It does not run on a timer or automatically after turns close. The `threadView.status` operation reports whether a compact is recommended based on the tail's token count against a configured threshold, but nothing triggers compact automatically.

Before assembly, compact reads record and derivation state as it stands. It does not call providers, schedule repair work, or re-queue failed derivations. If canonical record damage is detected — such as a turn referencing a missing chunk member — compact refuses before writing, leaving the prior view intact.

When a band entry depends on a derivation that is not ready, compact does not stop. It walks a fallback ladder: the smooth band tries `turn_rendering`, then `smooth_turn_compression`, then a deterministic excerpt of the turn's messages, then a gap. The detailed and brief bands try their primary chunk summary, then a concatenation of stored member material, then a gap. A gap is always the last resort, never the first response to a missing derivation. Chunk stored-member fallbacks are warning-logged; all degraded entries and gaps are recorded in the compact receipt and the stored view metadata.

```mermaid
sequenceDiagram
  participant C as user, agent, or harness
  participant V as thread-view
  participant T as threads
  participant U as turns
  participant M as messages
  participant F as thread file
  C->>V: compact
  V->>T: resolve ref to file path
  T-->>V: file path
  V->>U: read turns, chunks, derivation states
  V->>M: read message material for selection
  V->>F: write the view snapshot
  V-->>C: compact receipt
```

### Assembling the active model context

The context a harness consumes is assembled from the stored view snapshot (brief, detailed, and smooth bands) plus the current tail of recent messages. Assembling it is deterministic local work — reads and rendering — with no inference calls. An extensible harness can load `LlmRequestContext` without paying to re-derive anything.

Assembly selects already-derived artifacts; it does not create missing ones. If a band depends on a derivation that has not been derived yet, or that failed, the stored snapshot carries whatever the last compact wrote — degraded entries or gaps — and serves that.

Degrading is visible by obligation. A gap in band material renders as a marked gap in the view, so the agent reading it knows a stretch of history is thinner than it should be. The view never silently drops a span of the thread.

```mermaid
sequenceDiagram
  participant H as harness
  participant V as thread-view
  participant F as thread file
  H->>V: getLlmRequestContext
  V->>F: read stored bands and tail messages
  F-->>V: band snapshot and recent messages
  V-->>H: model context
```

### Tool results in the model context

Before an explicit smart compact, tail tool results render in full so resume and session-view stay faithful to the record. Smart compact is the planned reduction point for older material (via bands).

The **visibility boundary** controls at-or-behind shortening when it is set: tool results at or behind it render short, tool results ahead of it render full. Intake does not advance it automatically. Compact resets the boundary to the compact point.

### Rendering for a harness

The same assembled view renders in more than one form. An extensible harness that can take its context from LHC asks for `LlmRequestContext` as an in-memory message array. A closed harness that reads only its own session file gets the view written into a host-specific file format (today PI session JSONL) via `threadView.materialize`. Both come from the same serving assembly; only the output shape differs. A written file is a materialized rendering of the view, not a second source of truth: the thread file remains authoritative.

## Inspect

Inspect answers questions about a thread without changing it. The `inspect` domain produces three reports:

- **overview** — thread identity, event/message/turn/chunk counts, derivation state counts across both owners, the active view summary (or null if never compacted), and visibility boundary state. Deleted messages count separately; they are excluded from visible counts and token sums.

- **health** — derivation counts by owner, kind, and operational state; actionable failure detail (reason, attempts, last error) for failed and blocked derivations; a repair preview of currently failed (non-blocked) derivations that a requeue would target; and live queue visibility (queued vs claimed items).

- **view** — the stored view snapshot from `threadView.describe` (arrangement, gaps, config, per-band stored token counts, source-state provenance) plus the serving cost measured by running `threadView.getLlmRequestContext` and counting its output with the shared estimator. This makes the reported cost structurally identical to what an agent would receive.

Inspect is read-only and reads through the other domains' surfaces. It never writes, repairs, derives, or schedules work. It reports on whatever a person or agent asks and changes nothing.

```mermaid
sequenceDiagram
  participant C as host UI or agent
  participant N as inspect
  participant D as messages, turns, thread-view
  participant F as thread file
  C->>N: overview, health, or view
  N->>D: read through domain surfaces
  D->>F: read records
  F-->>D: records
  D-->>N: domain data
  N-->>C: report
```

I'd cut `inspect`.

It's the only domain that owns nothing — no tables, no derivations, no write path, no state transitions. Every operation it exposes is a composition of calls to other domains' public surfaces: `messages.report()`, `turns.report()`, `turns.listChunks()`, `threadView.describe()`, `threadView.getLlmRequestContext()`, `intakeStream.listEvents()`, `threads.info()`. The `health` report is derivation-state bucketing with failure detail — that's a natural fit for `turns` and `messages` to each expose on their own report surfaces (they already do the underlying `report()` queries). The reason it exists as a separate domain is a design taste choice, not a structural necessity: it enforces a "reads-only, imports no internals, owns nothing" discipline by being its own module. That's a valid organizational boundary, but it's not load-bearing the way the others are. Every other domain has something it exclusively owns — threads owns the registry, intake-stream owns the batch pipeline, messages owns projection and message-level derivations, turns owns the state machine and chunks and four derivation types, thread-view owns compact and the snapshot. Remove any of those and you're redistributing real state ownership and write paths. Remove inspect and you're moving three read-only composition functions.

The one argument *for* keeping it is that it prevents the other domains from growing "report about yourself in the context of the whole thread" methods that cross domain lines — `overview` reads from five domains, and no single one of them is the natural home for that join. But in practice, a `threads.overview()` that calls the other domains' surfaces is the same pattern inspect already uses, just without the separate directory.

Last question: what are the three biggest risks you see in this codebase as it heads toward an npm-published SDK consumed by a Claude Code wrapper? Short, direct answers.

**1. The SQLite dependency is Node-only and version-locked.** The entire persistence layer uses `node:sqlite`, which is experimental, landed in Node 22.5, and doesn't exist in Bun, Deno, or browsers. An npm-published SDK that requires Node 24+ with a specific built-in module cuts out a large chunk of potential consumers. `better-sqlite3` or `sql.js` would widen the surface, but the migration would touch every domain — the `DatabaseSync` type is threaded through everything.

**2. The pi-lhc connector's local type declarations will drift.** `src/pi/types.ts` mirrors PI's extension API from manual wiring research rather than importing from `@earendil-works/pi-coding-agent` types. Every PI release that changes a hook signature, adds a hook, or alters `SessionManager`/`ExtensionContext` shapes is a silent breakage that tests won't catch because the tests run against the local declarations. For an npm package consumed by Claude Code (which ships PI updates independently), this is a live compatibility risk on every upstream release.

**3. All inference is gated off or pinned to one model nobody else has.** `FORCE_TOOL_RESULT_SUMMARY_FALLBACK = true` means tool result summaries never run inference — they truncate. The default lane is `openai-codex/gpt-5.4-mini`, which is an internal model most external consumers won't have access to. A third-party Claude Code wrapper would need to configure every assignment manually, and there's no documentation or validation that tells them "your derivations are all falling back to truncation because your model isn't reachable" until they dig into `inspect.health`. The happy path for external consumers doesn't exist yet.
