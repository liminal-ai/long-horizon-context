# Comprehensive Repository Report: Long Horizon Context (LHC)

## 1. What this is

**Long Horizon Context (LHC)** is a durable context-management system for AI coding agents. The problem it solves: long-running agent sessions produce conversation threads that blow past LLM context windows. LHC records every event of a session to SQLite, derives compressed/summarized forms through an inference pipeline, and serves **"smart compact"** views — intelligently compressed histories that fit a token budget while preserving what the agent needs to keep working.

The architecture is a **single-login-free, in-process SDK** (`lhc`) consumed by **host harnesses** that adapt it to a specific coding agent. It never touches the network itself — all model calls are delegated back to the host through a callback boundary.

**Maturity:** the core SDK is production-shaped and exceptionally disciplined; the hosts are explicitly POC-grade but functional and dogfooded. ~75,000 lines of TypeScript, ~6 weeks of near-daily solo development (Jun 3 – Jul 12 2026), one primary author (Lee Moore, 234 commits), one co-identity ("T3 Code", 22 commits), one external PR contributor.

## 3. The packages

### 3.1 `lhc` — the core SDK (the crown jewel)

A Node library with **no CLI and no network**. The entire public API is `initLhc(config) → Lhc`, exposing domain namespaces: `threads`, `intakeStream`, `messages`, `turns`, `threadView`, `inspect`, `logging`, `work`.

**Domain model** (each domain owns one part of the conversation model and is reached the same way whether called by the host, another domain, or a future app-server endpoint):

- **Threads** — one durable conversation = one SQLite file (WAL mode). The file *is* the thread; a separate registry maps ids→paths as a lookup convenience, never authority. Thread ids are random (`th_`+hex); everything inside is deterministic positional (`t<n>`, `m<n>`, `c<n>`). Schema-versioned, migrates forward on open.
- **Intake stream** — the *only* content-entry path. Nine closed event kinds, closed schemas (unknown fields rejected structurally via Effect Schema), all-or-nothing batches, thread-scoped idempotency. Turn boundaries are decided **synchronously at intake**, never inferred later; exactly one open turn is a hard invariant.
- **Messages** — normalized readable view (typed blocks + token estimate). Owns two message-level derivations (smoothed prompt, tool-result summary) and edit/delete with cascade invalidation.
- **Turns** — turn state machine + chunk formation. Chunks group whole consecutive closed turns by a deterministic token-arithmetic policy (target 2200 / max 4400). Owns four turn/chunk derivations.
- **Thread view** — smart compact + serving. Four fidelity bands (full live tail → smooth → detailed → brief) as a *gradient, not a cliff*. Compact never calls a model — it's pure assembly from already-derived artifacts, with a fallback ladder (degrade over drop) and a hard refusal on canonical-record damage.
- **Inspect** — read-only reports (overview/health/view), reads through other domains' surfaces, changes nothing.

**Seven derivations** in a dependency hierarchy: 4 inference-backed (`smoothed_prompt`, `tool_result_summary`, `detailed_turn_compression`, `chunk_summary_brief`), 3 deterministic (`turn_rendering`, `pre_detailed_assembly`, `chunk_summary_detailed`). Each carries state (`pending`/`ready`/`failed`/`blocked`) and a `source_version` for optimistic concurrency.

**Shared-tech** (machinery with no domain surface, except logging): a **durable SQLite work queue** with claim/lease + **epoch fencing** + **source-version fencing** + FIFO no-skip-ahead; a **scheduler** (per-thread single-flight drain with pending-flag coalescing); an **inference adapter** (ModelCall → callbacks, input bounding, failure classification, timeout containment); a **prompt registry** (versioned name-keyed templates); an **instance seam** (AsyncLocalStorage scoping so multiple SDKs in one process never cross-drain); local **token counting** (`o200k_base`).

I read `sdk.ts` end-to-end and it is **genuinely excellent code**: the inference-config XOR validation (callbacks *or* config, never both/neither), exhaustive construction-time validation that *throws* on programmer error but returns `OpResult` for operational failure, the `scopeSurface` per-instance seam wrapping, and a clean `registerTestingWork` WeakMap seam that replaced an earlier leak of test hooks onto the runtime surface (documented in the bad-code-log as a fixed smell). The design discipline in the docs is faithfully reflected in the code I sampled.

### 3.2 `pi-lhc` — the PI connector (the reference host)

One package holding a **PI extension** + a **launcher binary**. Every PI message is captured into an LHC thread; PI's native compaction is intercepted and replaced by LHC smart compact; a session is seeded from the LHC thread view instead of a PI session file. The LHC thread is the durable record; the PI session is a rendering of it.

Highlights: an **observe-only hook rail** that never retains PI `ctx`/session objects (they're replaced each call), so `/reload` reconstructs cleanly. Capture is **lagged one hook by design** (PI persists entry ids *after* `message_end`). One LHC turn spans a whole agent run (`agent_end` closes it, not PI's per-step `turn_end`). Capture failures isolate into durable gap `runtime_note`s — nothing throws into PI. The compact bridge is a strict ladder that cancels loudly only on real failure (a 50k floor + genuine errors), with a `seed-entry-map` bridging LHC message ids → PI entry ids across session boundaries. **Largest known debt:** derivation inference rides PI's own model registry (a harness-mediated lane, contamination-adjacent) — the planned fix is the SDK-native inference lane (backlog 17/18).

### 3.3 `cc-lhc` — the Claude Code wrapper (POC)

A **PTY wrapper around the closed `claude` CLI**. Since Claude Code has no extension API rich enough, cc-lhc takes the *outside* position: owns the process, passes the terminal through transparently, and reaches LHC by two side channels — **watching the rollout JSONL** Claude Code writes (capture), and a **ctrl-] leader-key modal** on the alternate screen (control). Because it can't inject context into a running session, compact/prune **rebuild a fresh rollout file + inject `/resume <newId>`** to hot-swap the session in place.

This host contains the most impressive *systems-level terminal engineering* in the repo. The "output doctrine" (the wrapper never writes into a UI it doesn't own), the alt-screen modal that makes input ownership unambiguous by construction, leader recognition across three terminal encodings (raw / kitty CSI-u / xterm modifyOtherKeys), the swap-confirmation oracle (watch for the failure line *and* use rebuilt-rollout growth as ground truth), and failure-safe-by-construction resume — all of it reads as hard-won from live debugging. **This is exactly where your uncommitted WIP lives**: two modal-freeze fixes (kitty-encoded ctrl-C was dropped mid-command leaving no working detach key on kitty terminals; a stray string-terminator introducer wedged the modal) — now captured in `freeze-repro.test.ts`.

### 3.4 `codex-lhc` — the Codex wrapper (POC)

Key divergences from cc-lhc: Codex can't hot-swap, so compact/prune **kill-and-respawn** `codex resume <newId>`; Codex stores all sessions in one global date-dir tree, so discovery **requires a cwd filter** (without it, a concurrent Codex session in another workspace hijacks capture — found live); the mapper treats `response_item` as canonical and never intakes the `event_msg` layer (avoids double-writes). Same `claude -p` Sonnet-no-thinking inference lane as cc-lhc.

### 3.5 `t3code-lhc` — docs-only

Four markdown files: design + validation for a **"T3 Code" web host** (capture via provider runtime events, a shared swap controller with a "flip-last cursor invariant", deferred Grok/Cursor research, a Linux deployment handoff). **The implementation lives in a separate `liminal-ai/t3code` fork** — this package is the design record only.

### 3.6 `lhc-convex` — the Convex port (now on main)

A **from-scratch reimplementation of LHC as a Convex component** — the "web/desktop app server" future the core docs hinted at. It mirrors the domain decomposition on Convex's reactive backend (`convex/{schema,intake,queue,threads,view,work,inspect,logging,records}.ts`), plus a `src/client` + `src/shared` logic mirror and an `example/` host with both a fake and a **real OpenAI provider**, exercised against a live local Convex backend. Its `PORTING_LEDGER.md` reports **51 test suites ported / 1 n/a / 0 open**. Critically, it's built on the **`remove-queue-retries` pivot** (`3dd0b08`) — a one-shot work queue with no retry/backoff, because Convex owns scheduling/retry semantics itself. That pivot is a core-SDK change, which is why merging this to main changed trunk behavior for every host (§1 notes).
