# LHC Source Architecture: Complete Domain-by-Domain Analysis

## Entry Points

### `index.ts` — One-line re-export
Just `export * from "./sdk.js"`. All public API flows through `sdk.ts`.

### `sdk.ts` — The SDK Assembly (~400 lines)
The sole initialization function `initLhc(config: SdkConfig): Lhc` and the complete public surface. This file:

1. **Validates config** — XOR rule (exactly one of `inferenceCallbacks` or `inference`), mode must be `"background"` or `"manual"`, all numeric bounds positive/consistent.
2. **Resolves inference** — If `inference` config is given, validates the `ModelCall` function, merges per-derivation-kind assignments over defaults (smoothed_prompt → `codex/gpt-5.4-mini`, etc.), checks every prompt name against the `PROMPT_REGISTRY`, then builds an adapter into `InferenceCallbacks`. If direct `inferenceCallbacks` given, validates all 4 operations exist.
3. **Builds the `Lhc` object** — Assembles all 7 domain namespaces (`threads`, `intakeStream`, `messages`, `turns`, `threadView`, `inspect`, `logging`) plus `work`, `scheduler`, `config`, and `drainSettled`.
4. **Instance-scoped surfaces via `scopeSurface`** — Every domain function is wrapped through `runWithInstanceSeam(seam, fn)` so deep poke/touch calls reach THIS SDK's scheduler, never another's. Critical for multi-SDK isolation.
5. **Work handler registration** — Merges `messageWorkHandlers` (prompt_smoothing, tool_result_summary) and `turnWorkHandlers` (turn_derivation, detailed_turn_compression, chunk_summary_detailed, chunk_summary_brief) into the dispatch map. Work dispatchers map operation names to domain dispatch functions.
6. **Default inference lane** — `codex/gpt-5.4-mini` with target compression ratios (35–65% aim 50% for turn compression, 8–20% aim 12% for brief).

## Domain: `threads/` — Thread Creation and Registry

### `index.ts` — Thread CRUD surface
- **`newThread(input)`** — File-then-row creation with compensation. Creates the SQLite thread file first, then inserts into the registry. If registry insert fails, deletes the thread file. Blank paths rejected before any IO (the "vanishing temp database" fix).
- **`resolve({threadId})`** — Full or partial (prefix) ID resolution against the registry. Exact match wins; prefix must be unique or fails as `ambiguous_thread_id`.
- **`listThreads({cwd?, registryPath?})`** — All threads, optionally CWD-filtered.
- **`resolveThreadRef(ref)`** — The ONE interpreter of `ThreadRef` (either `{threadId}` or `{filePath}`). Every other domain calls this.
- **`info(ref)`** — Reads the thread file's own `thread_metadata` row (threadId, createdAt).
- **`openThreadDatabase(filePath)`** — Opens, validates, migrates, and fires `fireThreadTouch`.

### `internal/create.ts` — Schema and file management
- Defines the full SQLite schema: 15 tables including `thread_metadata`, `event`, `turns`, `message`, `message_block`, `work_item`, `derivation`, `chunk`, `chunk_member`, `thread_view`, `thread_view_band`, `view_boundary`, `log`, plus indexes.
- Thread creation seeds an initial open turn `t1` — the always-one-open-turn invariant starts at creation.
- `validateThreadFile` does read-only identity check (schema version, thread_metadata table/row).

### `internal/registry.ts` — Registry SQLite operations
- `~/.lhc/registry.sqlite` by default. Lazy-create on first write, never-create on read.
- LIKE-based prefix search with escaped metacharacters for partial-id resolution.
- CWD filtering via SQL WHERE, not post-filter.
- Insertion-order (`rowid`) breaks timestamp ties for deterministic `--continue`.

**Cross-domain calls:** threads calls nothing else; everything else calls threads.

## Domain: `intake-stream/` — Event Recording Pipeline

### `index.ts` — Public types and surface
- Defines the 9 event kinds as a discriminated union (`MessageEventInput`): user_prompt, assistant_text, assistant_thinking, runtime_note, model_change, thinking_level_change, tool_call, tool_result, turn_end.
- `BatchResult` reports per-event outcome (recorded/skipped), turn transitions, queued work, thread position.
- `messageEvents(ref, events)` and `listEvents(ref)` are the public surface.

### `internal/validate.ts` — Pure three-layer validation using Effect Schema
- **Layer 1** — Envelope: ThreadRef shape (closed struct).
- **Layer 2** — Event object: 5 required fields, event kind literal union.
- **Layer 3** — Per-kind payload: TextPayloadSchema, ToolCallPayloadSchema, etc. Turn_end enforces empty payload (no extra keys).
- Server-generated fields (`eventOrder`, `recordedAt`) rejected explicitly.
- `onExcessProperty: "error"` ensures unknown fields are never silently dropped.

### `internal/pipeline.ts` — The batch transaction
The core write path. Order is **load-bearing**:
1. Pure validation (no lock, no file open)
2. `createDbWriteTransaction` → `BEGIN IMMEDIATE`
3. Read existing idempotency keys (chunked to stay under SQLite parameter limits)
4. For each event in array order:
   - Skip if duplicate key (key-wins-over-content)
   - Insert event row, increment dense event_order counter
   - **Call `turns.create(transaction, recordedEvent)`** — handles turn state transitions
   - **Call `messages.create(transaction, recordedEvent, turnId)`** — projects event to message + queues work
5. Assemble BatchResult, COMMIT

**Cross-domain calls:** `messages.create()` and `turns.create()` — both synchronous, throwing on failure (rejects the whole batch).

## Domain: `messages/` — Message Projection, Derivation, Mutation

### `index.ts` — The messages surface (~350 lines)
- **`create(transaction, event, turnId)`** — Cross-domain, called by intake-stream. Projects event via `projectEvent`, inserts message row + blocks, queues work (prompt_smoothing for user_prompt, tool_result_summary for tool_result).
- **`list(ref, filter?)`** — Bounded read (from/to event-order, limit, includeDeleted). Attaches stored derivations per message.
- **`readLiveMessages(db)`** — In-transaction read for thread-view.
- **`show(ref, messageId)`** — Single-message detail with derivation report entries.
- **`report(ref)`** — Owner's derivation report (DerivationReportEntry[]).
- **`derive(ref, messageIds)`** — Synchronous derivation of specified messages.
- **`edit(ref, {messageId, content})`** — Edits content in closed-turn messages, cascades derivation invalidation.
- **`remove(ref, {messageId})`** — Deletes via tombstone, cascades. Refuses turn-initiating prompts.

### `internal/project.ts` — Event → message blocks
Pure mapping: each event kind becomes typed blocks. Token estimates come from `estimateTokens`. Turn_end → null (no message).

### `internal/store.ts` — Message row operations
Insert, read (bounded with deleted-filter), readById (audit/show, no deleted filter), applyMessageEdit (re-stamps content + token estimate), markMessageDeleted (tombstone).

### `internal/handlers.ts` — Message-level derivation work handlers
Two handlers registered: `prompt_smoothing` and `tool_result_summary`.
- **`smoothPromptHandler`** — Reads user_prompt text, runs `cleanPrompt`, checks token guard (over max → skip inference, use cleaned text). Calls `inferenceCallbacks.smoothPrompt`, validates output ratio (suspicious if output < ratio × input → discard with warning log).
- **`toolResultSummaryHandler`** — Reads tool_result content, finds paired tool_call by toolCallId, derives mechanical outcome, classifies tool result, calls inference. Small results (≤ smallTierTokens) pass through unchanged. `FORCE_TOOL_RESULT_SUMMARY_FALLBACK = true` currently forces truncation fallback for all tool results.

### `internal/classify-tool-result.ts` — Tool result classification (~350 lines)
Rule-based classifier producing `ToolResultClassification`:
- **operationClass**: read, mutation_write, mutation_edit, command, search_or_listing, verification, vcs_inspection, filesystem_mutation, multi_tool, unknown — derived from toolName + command patterns.
- **responseShape**: structured_receipt, simple_failure, no_output, search_result, test_result, file_content, diff_output, large_log, etc.
- **promptMode**: receipt, failure, search_summary, test_summary, etc.
- **facts**: Parsed from output — exitCode, targetPath, matchCount, testSummary, searchMatches, pathMentions, etc.

### `internal/cascade.ts` — Mutation cascade engine
Walks the derivation chain upward from a mutated subject: message → turn → chunk.
- Edit: clears all derivations in the chain, re-queues at next source version.
- Delete: drops the message's own derivations, clears upward chain.
- Finds paired tool counterpart (tool_call ↔ tool_result) and cascades that too.
- Supersedes still-queued old-version items.

### `internal/derive.ts` — Synchronous message derivation
Runs message derivation outside the queue: validates message exists, finds the derivation kind (user_prompt→smoothed_prompt, tool_result→tool_result_summary), runs the handler, applies the result with version-checked write. Also used by `dispatchMessageDeriveWork` for durable queue dispatch.

### `internal/smoothing.ts` — Deterministic prompt cleanup
`cleanPrompt(text)`: normalizes whitespace, collapses blank lines, capitalizes "i", preserves fenced code blocks verbatim. Pure function, no IO.

### `internal/work.ts` — Kind ↔ derivation mapping
Maps event kinds to work kinds: `user_prompt → prompt_smoothing`, `tool_result → tool_result_summary`. And work kinds to derivation types: `prompt_smoothing → smoothed_prompt`, etc.

**Cross-domain calls:** Called by intake-stream's pipeline. Calls `threads.resolveThreadRef`, `threads.openThreadDatabase`. The cascade calls `shared-tech/work-queue`.

## Domain: `turns/` — Turn State Machine, Composition, Chunks

### `index.ts` — Turns surface
- **`create(transaction, event)`** — Cross-domain, called by intake-stream. The state machine:
  - `turn_end` with members → close current, open new
  - `user_prompt` with members → close current, open new (implicit turn boundary)
  - Everything else → no transition, return current open turn's ID
  - Empty turn on turn_end → ignored (no close)
  - Closing queues `turn_derivation` work (with two derivation targets: turn_rendering + pre_detailed_assembly)
- **`listTurns(ref)`** / **`listChunks(ref)`** — Read-back with derivations.
- **`getChunkText(transaction, chunkId)`** — Chunk material for compact.
- **`readTurnChunkStructure(db)`** — Structure for thread-view's compact selection.
- **`report(ref)`** — Owner's derivation report.
- **`deriveTurn(ref, turnId)`** / **`deriveDetailedChunk`** / **`deriveBriefChunk`** — Synchronous derivation.

### `internal/store.ts` — Turn row operations
Open turn selection, member counting, turn close, turn reads (with deleted filter for listings, without for structure).

### `internal/derive.ts` — The heart of the derivation pipeline (~500 lines)
Four work handlers:
1. **`turnDerivationHandler`** — Deterministic. Reads member messages + their derivations, composes `turn_rendering` (structured part-by-part text with tool-run grouping) and `pre_detailed_assembly` (dialogue-register: user prompts + assistant text only). On completion, places the turn into a chunk and enqueues `detailed_turn_compression`. Recovers message-level derivation floors when needed.
2. **`detailedTurnCompressionHandler`** — Inference-backed. Reads pre_detailed_assembly, calls `inferenceCallbacks.compressDetailedTurn` with target token ratios. Tiny turns (< tinyTurnTokens) pass through unchanged. On inference failure after exhausting retries, falls back to pre_detailed_assembly content with fallback metadata.
3. **`chunkDetailedHandler`** — Deterministic concatenation of member turns' detailed_turn_compression content with tool-run receipts. Falls back to pre_detailed_assembly for failed members.
4. **`chunkBriefHandler`** — Inference-backed. Reads chunk_summary_detailed content, calls `inferenceCallbacks.summarizeChunkBrief`. If detailed not ready, defers (enqueues detailed first, then re-enqueues brief).

### `internal/chunks.ts` — Chunk placement and close policy
`placeTurn(db, turnId, projectedTokens, policy)`:
- If open chunk + incoming ≥ target → close chunk, start new one
- If incoming alone ≥ max → close immediately after placing
- Default policy: target 2200 tokens, max 4400 tokens per chunk
- `enqueueChunkSummaries` → enqueues both detailed and brief summary work items.

### `internal/compose.ts` — Turn rendering composition (~500 lines)
The pure composition engine. `composeRenderingInput(messages, derivations)`:
- Builds per-message atoms: ready derivation content verbatim, or raw/truncated fallback
- Groups consecutive tool activity into maximal runs with receipts
- Composes structured text with labels, outcomes, run headers
- `composePreDetailedAssembly` → dialogue-register (user prompts + assistant text only)
- Tool runs account succeeded/failed/unknown with receipts

### `internal/derivations.ts` — Turn-owned derivation reads
Source reads for handlers: turn source, member messages, message derivation rows, member projections for chunks. Report surface joins derivation rows with live work_item queue status.

### `internal/chunk-recovery.ts` — Chunk material fallback
When chunk summaries aren't ready, `storedMemberConcat` builds concatenated raw content from members' message blocks as a fallback.

**Cross-domain calls:** Called by intake-stream's pipeline. Calls `messages.create` indirectly (through `writeMessageDerivationFloorInThread`). Reads message tables directly for composition.

## Domain: `thread-view/` — View Assembly and Smart Compact

### `index.ts` — Thread view surface (~400 lines)
- **`getLlmRequestContext(ref)`** — Hot-path read returning messages for LLM context. Assembles from stored snapshot bands + tail messages.
- **`getSessionThreadView(ref)`** — PI-session-native format (user/assistant/toolResult entries).
- **`status(ref)`** — Tail token count, compact recommendation (tailTokens > threshold), derivation state counts, visibility zone.
- **`describe(ref)`** — Stored snapshot read-only.
- **`previewCompact(ref, opts)`** — Read-only compact preflight.
- **`compact(ref, opts)`** — The write operation: validates profile, reads record + derivations, runs selection, renders bands, atomically replaces snapshot + resets boundary.
- **`materialize(ref, opts)`** — Writes PI session JSONL file from assembled view.

### `internal/profiles.ts` — View configuration
Three built-in profiles:
- **continuation**: 30% full, 30% smooth, 20% detailed, 20% brief (120k lower bound)
- **conversation**: 12% full, 48% smooth, 20% detailed, 20% brief
- **coding**: 25% full, 35% smooth, 20% detailed, 20% brief
- Default visibility: 64k max, 32k target
- Default compact threshold: 160k tokens

### `internal/select.ts` — The pure selection walk (~400 lines)
`selectArrangement(inputs, config)` — the core algorithm:
1. **Compact point** — Walk messages newest-first until token sum ≥ full budget; snap to turn boundary.
2. **Smooth band** — Banded closed turns newest-first, fill until budget.
3. **Detailed band** — Closed chunks entirely older than smooth, newest-first fill.
4. **Brief band** — Remaining chunks after detailed, newest-first fill.
5. **Coverage gaps** — Any banded turn not represented gets a coverage entry with best available derivation.
`readSelectionInputs(db)` does corruption checks before selection (open-turn invariant, referential integrity).

### `internal/assemble.ts` — View assembly
Reads stored snapshot bands + tail messages, renders them into `AssembledViewEntry[]`.

### `internal/render.ts` — Band and tail message rendering
Renders band content as user messages with `[context · brief/detailed/smooth]` headers. Tail messages mapped by kind to role (user_prompt→user, assistant_text→assistant, tool_result→toolResult with boundary-based shaping). Tool results behind the visibility boundary render short.

### `internal/session-view.ts` — PI session format
`buildSessionThreadView(db)` → bands as user context messages, tail as typed entries (user/assistant with parts/toolResult). Groups consecutive assistant messages (thinking/text/tool_call) into single assistant entries with content parts.

### `internal/snapshot.ts` — Stored view CRUD
Reads/writes the singleton `thread_view` row + `thread_view_band` rows. `replaceViewSnapshot` atomically replaces in one transaction (delete old → insert new → reset boundary).

### `internal/boundary.ts` — Visibility boundary
Reads the singleton `view_boundary` position. `visibilityZoneTokens` computes live tool results ahead of both boundary and compact point.

### `internal/compact-compute.ts` — Compact arrangement computation
Bridges selection inputs + chunk materials with the selection walk. Checks whether a compact would advance the stored point.

### `internal/seam.ts` — Test injection point
`fireViewInjection("compact-write")` — test seam for stopping compact at the write boundary.

**Cross-domain calls:** Calls `messages.readLiveMessages`, `turns.readTurnChunkStructure`, `turns.getChunkText`, `messages.report`, `turns.report`, `threads.resolveThreadRef`, `threads.openThreadDatabase`.

## Domain: `inspect/` — Diagnostic Reports

### `index.ts` — Three report surfaces
Pure consumer of other domains. Imports NO internals, owns NO tables, writes NOTHING.
- **`overview(ref)`** — Thread identity, event/message/turn/chunk counts, derivation state counts, view summary.
- **`health(ref)`** — Derivation state bucketing, failure detail with attempts/lastError, repair preview (requeue targets), capture gap detection from runtime_note events.
- **`view(ref)`** — Stored snapshot from `threadView.describe` + serving cost from `threadView.getLlmRequestContext`.

**Cross-domain calls:** Calls `threads.info`, `threads.resolve`, `intakeStream.listEvents`, `messages.list`, `messages.report`, `turns.listTurns`, `turns.listChunks`, `turns.report`, `threadView.status`, `threadView.describe`, `threadView.getLlmRequestContext`.

## Shared Technical Infrastructure: `shared-tech/`

### `context.ts` — AsyncLocalStorage-based per-SDK instance scoping
- `runWithInstanceSeam(seam, operation)` — Every SDK operation runs inside this.
- `resolveInstancePoke()` / `resolveInstanceViewConfig()` / `resolveInstanceConfig()` — Current SDK's seam.
- `runWithThreadTouchSuppressed(operation)` — Read-only operations suppress the thread-touch announcement.
- `fireThreadTouch(filePath, db)` — Thread-file open announcement for scheduler catch-up.

### `errors.ts` — Error vocabulary
20+ error codes across 3 error classes (caller_error, state_corruption, system_error). `OpResult<T>` union type used everywhere.

### `storage.ts` — SQLite primitives
`openDatabase(path)` with WAL mode, foreign keys, busy timeout, synchronous=NORMAL. Schema version tracking.

### `derivation.ts` — Complete type vocabulary (~300 lines)
All derivation types: `SubjectKind`, `DerivationState`, `ToolOutcome`, `Derivation`, `DerivationMetadata`, `ToolRunReceipt`, `InferenceCallbacks` (4 operations), `HandlerOutcome`, `HandlerDerivationWrite`, `SdkConfig`, `ResolvedSdkConfig`, tool-result classification types.

### `scheduler.ts` — Background drain scheduler (~350 lines)
- `createScheduler(mode, deps)` — Per-thread single-flight drain with pending-flag coalescing.
- Background mode: poke → schedule macrotask drain → runLoop (repeated while pending) → armWake (for retry backoff or claim expiry).
- `drainOpenDb` — Claim → dispatch → complete loop, one item at a time.
- `runDrain` — Opens thread file, drains, closes.
- `drainSettled(threadId)` — Promise that resolves when no drain is running/pending/waking.

### `work-queue/index.ts` — Durable work queue
`enqueue`, `claimNext` (FIFO with lease), `retryClaimedItem`, `supersedeQueued`, `countLiveItems`. Items carry `claim_epoch` for epoch-fenced coordination.

### `durable-work/index.ts` — Derivation completion mechanics
`applyDerivationSuccess` — Version-checked UPDATE in one transaction with post-commit hooks. `applyDerivationTerminalFailure` — Marks derivation failed/blocked. `runWorkHandler` — Safe wrapper around handler execution.

### `inference-adapter.ts` — ModelCall → InferenceCallbacks adapter
Builds InferenceCallbacks from a host-supplied `ModelCall` function + per-kind assignments. Applies prompt templates, input bounding, timeout, empty-output classification, and provenance stamping.

### `inference-types.ts` — Inference config and guard types
`ModelCall`, `ModelAssignment`, `InferenceConfig`, derivation guards (smoothedPrompt.maxInferenceTokens, etc.).

### Other shared-tech modules
- **`classify.ts`** — Failure classification (retryable vs terminal)
- **`deterministic.ts`** — Test-double inference callbacks
- **`persist.ts`** — `createDbReadTransaction`/`createDbWriteTransaction` helpers
- **`report.ts`** — `reportEntryFromRow` for owner report surfaces
- **`inspect.ts`** — Report types (HealthReport, InspectOverview, ViewContentsReport)
- **`view.ts`** — View config types (ViewProfile, VisibilityBudgets, StoredView, SessionThreadView)
- **`tool-result-rendering.ts`** — `truncateForFallback` helper
- **`thread-migrate.ts`** — Schema migration across versions
- **`token-counting/index.ts`** — `estimateTokens` via js-tiktoken (o200k_base)
- **`logging/`** — Structured log + derivation audit log with `writeLog`/`queryLog`/`appendDerivationLog`
- **`prompts/`** — Versioned prompt templates: smoothing-v1, tool-result-v1/v2, detailed-turn-compression-v1/v2, chunk-brief-v1/v2

## Cross-Domain Call Graph

```
intake-stream  ──calls──→  turns.create()      (turn state machine)
               ──calls──→  messages.create()    (projection + work queue)

messages       ──calls──→  threads.resolveThreadRef, openThreadDatabase
               ──calls──→  shared-tech/work-queue (enqueue, supersede)
               ──calls──→  shared-tech/token-counting

turns          ──calls──→  messages (writeMessageDerivationFloorInThread for recovery)
               ──calls──→  shared-tech/work-queue (enqueue, hasLiveItem)
               ──reads──→  message tables directly (for composition)

thread-view    ──calls──→  messages.readLiveMessages, messages.report
               ──calls──→  turns.readTurnChunkStructure, turns.getChunkText, turns.report
               ──calls──→  threads.resolveThreadRef, openThreadDatabase
               ──calls──→  shared-tech/token-counting

inspect        ──calls──→  ALL domain surfaces (pure consumer, no internals)

sdk.ts         ──calls──→  ALL domains (assembly + scoping)
               ──calls──→  shared-tech/scheduler (createScheduler)
```

The architecture enforces strict ownership: each domain owns its tables and derivation types. Cross-domain reads go through public surfaces or designated cross-domain functions. The work queue and scheduler are shared infrastructure that domain handlers register into. The `inspect` domain is deliberately the most restricted: it owns nothing, writes nothing, and consumes everything through public APIs only.
