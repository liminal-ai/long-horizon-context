# Merge brief — long-horizon-context
- Merge only with `~/.agents/skills/poteto-mode/scripts/merge-gate/merge-gate --repo liminal-ai/long-horizon-context --pr <n>`, on GitHub through `gh`. The gate's default squash merge is this repo's method.
- `pnpm run lint` and `pnpm run typecheck` pass at the repo root before the PR-facing push. CI `pr-checks` jobs `root`, `lhc`, `claude-lhc`, `cc-lhc-mod` and `cc-lhc` (`.github/workflows/pr-checks.yml`) pass at the head.

| each package | its own skill: `packages/lhc` → `verify-lhc`, `packages/claude-lhc` → `verify-claude-lhc`, `packages/cc-lhc` and `packages/cc-lhc-native` → `verify-cc-lhc`, `packages/cc-lhc-mod` → `verify-cc-lhc-mod` |

- Perf bar for `verify-claude-lhc`. Run `drive.mjs all` warm three times on base and three times on head, interleaved, with `MEMBASE_REPO` set, and compare with `.agents/skills/verify-claude-lhc/perf-compare.mjs`, which takes both SHAs and the six `summary.json` files in sample order. It fails unless base has seeded drives and every one of them passes in all six runs, the head median of their summed times stays within 20 percent of base's, and each head run's seeded drives together finish inside 10 minutes. The verdict states that the runs were warm and interleaved, which the files cannot show. A plan may add a bar of its own, never loosen this one.
- A multi-PR program also runs that comparison between its final main and the main it started from, before it closes, with `perf-compare.mjs --report-only`, because each PR's 20 percent compounds. The claude-lhc-host-ready program passed every per-PR bar, yet its five shared seeded drives rose 33.5 percent while host latency rose about 30 ms (`.pstack/runs/claude-lhc-host-ready/proof/cumulative-perf/report.md` in the main checkout). The closing report explains any increase past 20 percent.
- Same-head re-verdict. When a FAIL comes only from a criterion the lead wrote, such as a plan rule or a lane prompt, and not from the code, the lead may correct the criterion and run a fresh verdict at the same head. That verdict may carry the earlier lanes as shortcuts. It states the corrected criterion, and the criterion names the defect, not its worst observed symptom. For example, "an automatic compact runs with no new context since the previous one" names a defect. "Base loops forever" names a symptom, and base in fact re-compacted two or three times and then answered.
- The verifier posts its own verdict as a PR comment whose first line is `pstack-verdict: <PASS|PASS+NOTES|FAIL> head=<sha> base=<sha> by=<model>`. The gate reads only lines from the repo's owners, members or collaborators. Under it the verdict lists each plan box once, as `box <id>: done`, `n/a. <reason>`, `skipped. <what did not run>` or `changed. <who accepted the changed bar>, <why>`. A box id matches `[a-z]+(-\d+)?`, such as `live-2` or `seam`, so `live-2a` or `Live-2` does not parse. A box listed twice fails the gate. The verdict also lists, by the table's exact skill and drive names, every check the diff triggers, once each, as `check <name>: done`, `check <name>: carried. <source head>, <reason>` or `check <name>: skipped. <reason>`. A skipped required check needs the lead's acceptance on the PR or a named deferral owner, as `--accept-skip` and `--defer` do for plan boxes, because a disclosed skip is not a satisfied check. A plan's verify boxes add to this list and never replace it. Until the gate's parser enforces this list, the lead does.
- A program PR is gated against its plan section: `--plan <plan file> --plan-pr <id>`, such as `--plan-pr CCV2-6`, or the PR body's `pstack-plan: <file> pr=<id>` line. The verdict must list every verify box of that section. The lead answers what the verdict leaves open with repeatable flags, each posted on the PR before the merge: `--accept-shortcut <id>=<reason>` for a lane the re-verification carried, `--accept-skip <id>=<reason>` for a skipped box that does not apply, and `--defer <id>=<owner>` for a skipped box whose work is owed, the owner being a Linear id such as `LH-247` or an open workflow step.
- A verify-skill check must fail when the evidence its outcome needs is missing or wrong. A PR that adds or changes such a check names a broken-case probe that runs it on a deliberately broken input and shows it failing, then on the good input and shows it passing. The verdict cites both outputs. `verify-cc-lhc/helpers/probe-checks.sh` is the pattern. Lee set this rule in the 2026-11-06 retro. Such a check grades against the product's own outputs, such as its exported mapping functions and canonical views, never against a hand-written copy of the product's rules, which drifts.
- Review bots and their lanes are in `.github/REVIEW_RULES.md`. Codex must review the head commit. After a push, or when its review names no commit, comment `@codex review` on the PR.
- Authorized exception: a Codex review stuck at "running" may be waived with `--waive codex=<reason>` only when an independent verdict already covers the head, and the reason names the stuck run and that verdict ([#35](https://github.com/liminal-ai/long-horizon-context/pull/35)).
- Owners stop at code-ready on a pushed branch. Only the lead merges, retargets, rebases a chain or force-pushes a shared branch, even where a playbook lets owners merge.
- A change to `AGENTS.md` or `CLAUDE.md` needs Lee's approval of the exact text (`~/lim-v2/AGENTS.md`).
