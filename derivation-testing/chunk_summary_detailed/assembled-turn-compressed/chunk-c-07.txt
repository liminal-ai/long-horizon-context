You’re right that if the input contains code, smoothing should not rewrite the code itself. Since smoothing is supposed to be light-touch — typo fixes, capitalization, whitespace normalization — the value is in the prose, not the code. So the real design choice is: do we bypass smoothing entirely when code is present, or do we split the input into chunks and smooth only the non-code parts?

The strongest argument for chunking is that it strictly dominates bypassing. If the prompt is all code, chunking naturally degenerates to “do nothing” because there’s no prose to smooth. If the prompt mixes prose and code, chunking lets us smooth the prose while leaving fenced code verbatim. That preserves the benefit where it exists, instead of throwing it away with a blanket bypass. It also gives a structural guarantee: the code never goes to the model at all, so we’re not relying on the model to obey “don’t touch fenced code.”

That said, chunking introduces fence-detection and reassembly edge cases: unclosed fences, inline backticks, indented code blocks, etc. But the failure modes are acceptable and bounded. A mis-segment might slightly over-smooth a bit of code, or leave a bit of prose raw. That’s much better than a brittle system that can silently mangle fenced content or get stuck.

On the deterministic transform layer: yes, there’s likely an upfront non-model pass that can normalize whitespace and maybe handle some trivial capitalization before summarization. That matters because it changes the architecture of smoothing. The deterministic layer can raise the fallback floor: if the model smoothing fails or is skipped, we can still serve a deterministic-smoothed version instead of raw text. That’s strictly better than today’s “raw fallback.” But it also has to be fence-aware for the same reason as the model layer: it should not normalize whitespace inside code.

On prompt length, I agree there’s a real threshold where smoothing stops being worth it. Something like 5k or 10k tokens may be too expensive to run through the model just for typo cleanup. The key point is that the length cap should apply only to the model smoothing step, not the deterministic transform. If we chunk first, the cap should measure model-bound prose only, not the entire prompt. So a 10k-token prompt that is mostly code with a small prose introduction shouldn’t be penalized as a 10k smoothing job.

That choice also changes the error model. With unconditional smoothing, the states are basically success, provider failure, or source-blocked. With chunking plus a cap plus a deterministic floor, we get a new intentional outcome: “skipped because too long” or “skipped because there was nothing to smooth.” That is not an error. It should land in `ready`, not `pending`, and should not retry. It also should not be treated as degraded if deterministic-only output is the intended result. In other words, skip and fail can look similar in output quality, but they have different semantics.

So the open decisions are:

1. **Chunk vs bypass for code-containing input**  
   I lean chunk, because it preserves prose smoothing and guarantees code safety.

2. **Where the deterministic transform lives**  
   Either at intake as a cheap floor-raising step, or inside the handler. Intake gives a better fallback result; handler-local keeps the hot path simpler.

3. **Whether “skip” becomes a first-class ready outcome**  
   If we adopt the richer behavior, skipped smoothing is an intentional terminal state, not an error.

This is all SDK smoothing-handler behavior, i.e. Epic 5 / dial-in territory, not the pi-lhc Epic 2 work. The only place it affects serving is in how we interpret a `smoothed_prompt` that is deterministic-only, failed, pending, or intentionally skipped.

Short answer: **no — not segmentation plus classification**. It’s too much mechanism for this derivation, and it’s the brittle extreme your nonlinear-cost principle warns against.

Why:

1. **Smoothing is low-value.** It mainly fixes typos, caps, and whitespace. The fallback is the **raw prompt**, which is lossless, and models already tolerate noise well. So the payoff is mostly cosmetic. Building a segmentation/classification engine to protect a thin prize is effort-inverted.

2. **What matters is narrow safety:** don’t let the smoother corrupt code in the bands. But segmentation is the expensive way to solve that. A prompt instruction like **“fix typos/capitalization/whitespace; leave fenced code and literal strings verbatim”** gives most of the protection at near-zero cost, with no brittle routing logic. It’s trust-based and may slip sometimes, but the downside is small.

3. **Classification adds complexity out of proportion to the stakes.** Per-segment decisions, reassembly, fence edge cases — you’d be importing the brittle-regex problem into a derivation whose fallback is simply “serve the raw prompt,” which is acceptable.

The one counterpoint: **deterministic whitespace normalization is free and can corrupt code**, so if you want that free deterministic floor, you’d need fence awareness. But that argues for cheap fence detection, not full segment-classify-and-route.

So my lean: **use prompt instructions for code/literal safety, skip the segmentation engine**. I’d reconsider only if code-embedded-in-prose prompts are common in real usage and smoothing proves meaningfully valuable in dogfooding.
