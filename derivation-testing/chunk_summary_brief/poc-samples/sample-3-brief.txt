PI Long Horizon is a managed-memory harness for PI to continue coding sessions past one context window. Core v1 loop was manual and inspectable: capture canonical session state, maintain derived memory artifacts, inspect readiness/blockers, run smart compact, continue in a generated PI session.

Durable decisions:
- Canonical thread is the full source of truth; generated/compacted PI sessions are disposable projections and must never replace it.
- Memory is organized semantically: prompt-bounded turns, then older closed turns grouped into chunks.
- Projection uses fidelity bands: raw recent turns, smooth turns, detailed chunk summaries, brief chunk summaries.
- Compaction/projection should be traceable and explicit about degraded/blocker states rather than silently omitting context.
- Async maintenance owns turn closing/repair, smoothing, chunking, summarization, and readiness reporting.
- Attach/import must bring existing PI sessions under management without losing prior history.

Architecture boundaries were intentionally separated: domain records, file-backed local store, capture/import, async maintenance, projection/compiler, PI target writer, thin PI extension.

Important lasting conclusions:
- The implementation largely matched and strengthened the original design.
- The most important distinction is canonical truth vs prompt-visible/generated projection.
- Band allocations are heuristic shaping parameters, not exact quotas.
- A major practical later addition was message-level tool-result truncation/off-gassing, because turn/chunk banding alone does not handle huge live tool output.

Critical degraded states to surface:
- turn repair needed
- stale/missing smoothing, chunking, summaries, or token counts
- projection not trustworthy
- active PI session not latest/generated/managed
