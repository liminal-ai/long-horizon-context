The user asked whether the earlier reconstruction was comprehensive or merely high-level, and requested the most comprehensive memory possible. The response expanded the remembered PI Long Horizon design substantially.

PI Long Horizon was described as a long-horizon coding-agent harness on top of PI, intended to preserve coding-session continuity beyond a single context window by maintaining a managed memory substrate over a canonical session. The v1 loop was explicitly manual and inspectable: capture session, maintain derived memory, inspect state, run smart compact, then continue in a generated PI session. Full automation was not the initial goal.

Core domain concepts recalled:
- Canonical thread/thread as durable full-fidelity source truth.
- Messages and structured message parts as captured PI units.
- Prompt-bounded turns as the main semantic unit: user prompt starts a turn; assistant/tool activity remains in that turn until the next prompt.
- Closed turns as eligible for smoothing, chunking, and projection.
- Smooth turns as per-turn compressed representations.
- Chunks as groups of older closed turns.
- Fidelity bands for stratified memory.
- Projections as derived, prompt-visible renderings of canonical state.
- Generated PI sessions as disposable compacted outputs.
- Maintenance state for async readiness, blockers, and degraded modes.
- Import/attach for bringing existing PI sessions under management.

Key product principles:
- Preserve canonical source truth; generated sessions must never replace it.
- Make compaction inspectable.
- Prefer explicit blockers/degraded states over silent failure.
- Use semantic units like turns and chunks instead of arbitrary transcript slices.
- Treat generated output as a projection/revision, not durable record.
- Start with manual smart compact for v1/dogfood use.

The memory model was stratified by age and fidelity. Recent context should remain closest to raw transcript, while older context is progressively compressed. Four bands were recalled: raw/full-fidelity recent turns, smooth turns, detailed chunk summaries, and brief chunk summaries. Band allocation was understood as budget-shaped selection rather than exact quota fulfillment.

Smoothing was asynchronous and intended to preserve user intent, decisions, files touched, important facts/results, and unresolved follow-ups while dropping verbose detail. Chunking grouped older closed turns so lower-fidelity history could be represented by detailed or brief summaries. Missing or stale derived artifacts were expected to produce visible degraded/blocking states rather than silent substitution.

The smart compact flow was remembered as: capture canonical state; ensure turns are closed/repaired; ensure required async artifacts exist or report blockers; build a projection/thread view from canonical state and artifacts; allocate context across bands under budget; emit a generated PI session; have PI load it; record source/projection revision metadata. Generated sessions should be traceable to canonical source revision and projection revision, and the system should know whether PI is on a generated/latest rollout.

Attach/import was important: existing PI sessions should be read into a canonical thread, turns inferred and possibly repaired, and future capture continued without losing pre-extension history.

Architecture boundaries were recalled as local/file-backed and inspectable, with separation among domain records, file store, capture/import, async maintenance, projection services, PI target writer, and extension commands/events. The PI extension should remain thin but operationally important: observe lifecycle/session events, capture messages, expose status, trigger smart compact, and cause PI to reload generated sessions. It should not own canonical truth.

Async maintenance was fundamental: closing turns, smoothing, chunking, summary generation, readiness updates, and blocker reporting. Visible failure/degradation states were important for turn repair needed, stale/missing smoothing or summaries, stale token counts, untrusted projections, unmanaged sessions, or PI not running the latest generated rollout.

The docs clearly cared about fitting a target context budget, but exact token accounting was remembered as less developed than in the later implementation. Later code matured this with provider-backed counts, final count enforcement, reduction loops, thread-view IR, active prompt projection, richer reports, fixture/eval tooling, rollout reconciliation, mutation leasing/concurrency guards, and prompt-visible tool-result truncation.

The major architectural idea was compiler-like: canonical thread plus derived artifacts plus budget policy produce a PI-compatible generated session. The central success was preserving the distinction between canonical source truth and generated prompt-visible projection. A key later practical addition was message-level tool-result off-gassing/truncation, since turn/chunk banding alone cannot handle huge recent or active tool outputs.
